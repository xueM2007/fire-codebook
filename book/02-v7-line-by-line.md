# 第 2 章　v7 逐行精读：一片火如何跨过第 64 列

**这一章你会得到什么**：能从一枚字符追到一个字中的一位，再追到下一拍、下一行和输出文件。代码框保留原文件物理行号；每条解释里的短代码是定位标记，整行以代码框为准。看到空行、括号时也标明它分隔哪两件事。

## 第 1–25 行 · 先把时钟和入口接好

**这段在干什么**：这段只建立计时方法并检查两个文件名，不碰森林。程序启动后拿到的是一组字符串，两个路径由启动者给，不能假定运行目录就是输入所在处。

**先认写法**：先认三种标点。#include（header inclusion，包含头文件）让后面的声明可见；::（scope resolution，作用域限定）告诉编译器去哪个命名空间或类型找名字；[](...) {...}（lambda expression，匿名函数表达式）做出一个可调用的对象。它们分别回答‘声明从哪来’‘名字属于谁’‘这段操作如何被反复调用’。

**代码块**：

```cpp
  1  #include <iostream>
  2  #include <vector>
  3  #include <chrono>
  4  #include <cstdio>
  5  #include <cstdint>
  6  #include <cstddef>
  7  #include <omp.h>
  8  #include <algorithm>
  9  
 10  namespace {
 11      using Clock = std::chrono::steady_clock;
 12  }
 13  auto ms_since = [](Clock::time_point t0) {
 14      return std::chrono::duration<double, std::milli>(Clock::now() - t0).count();
 15  };
 16  
 17  int main(int argc, char** argv) {
 18      auto t_all = Clock::now();
 19      auto t0 = Clock::now();
 20  
 21      if (argc < 3) {
 22          std::cerr << "用法: " << argv[0] << " <输入文件> <输出文件>\n";
 23          return 1;
 24      }
 25  
```

**逐行讲解**

**第 1 行** · `#include <iostream>`

输入输出流（input/output stream，按顺序收发字符的对象）来自 iostream。这里后续只需要错误流 cerr；头文件名里的 io 不表示地图一定会用 cin 读。没有直接声明就依赖其他头偶然包含它，不稳妥。

**第 2 行** · `#include <vector>`

向量（vector，能管理一段连续元素的容器）由这个头文件提供。后面的 `vector<char>` 和 `vector<uint64_t>` 是同一模板配两种元素，前者数的是字符，后者数的是字，不可把容量单位混用。

**第 3 行** · `#include <chrono>`

计时库（chrono，表示时刻和时长的标准库）给出后面所需的时钟与单位。只有两个时刻做差才是时长；直接拿某个时刻当毫秒数没有这里需要的含义。

**第 4 行** · `#include <cstdio>`

标准 C 文件接口（C standard I/O，以文件流指针读写的接口）在 C++ 里通过 cstdio 声明。它让读写操作明确给出元素大小和个数，后面的短读检查就靠这个返回约定。

**第 5 行** · `#include <cstdint>`

固定位宽整数头文件 cstdint 声明 uint64_t 等类型（在支持精确位宽的目标上）。后面的 63、64 都是根据整字恰好 64 位设计的，随手改成 unsigned int 会破坏跨字逻辑。

**第 6 行** · `#include <cstddef>`

大小类型（size type，能表示对象大小的无符号整数类型）由 cstddef 等头提供，标准名字是 std::size_t；本文件用未限定的 size_t。不能从‘无符号’推导出所有输入都安全，负数转换后可能变成很大的正数。

**第 7 行** · `#include <omp.h>`

共享内存运行库的声明来自 omp.h。第 113、114 行普通函数会查团队大小和编号；仅能找到头文件不保证产生并行代码，也不保证链接器能找到函数定义。

**第 8 行** · `#include <algorithm>`

算法头 algorithm 声明取小值 min 和区间填充 fill。后者在第 174、185 行专门清除边沿的旧火，和默认构造时只清零一次不是一回事。

**第 9 行**

空行把头文件与本文件自己的名称隔开；不参与编译逻辑，删掉不改变结果。

**第 10 行** · `namespace {`

命名空间（namespace，给名字划出作用范围）在这里没有名字，内部声明只供这个翻译单元使用。它不是函数，不制造线程，不需要像定义类那样在闭括号后放分号。

**第 11 行** · `using Clock = std::chrono::steady_clock;`

类型别名（type alias，给现有类型换短名）用 using 创建。steady_clock 是单调时钟，适合算经过时长，不能把它的读数当作今天几点；后面改用 Clock 时指的仍是同一类型。

**第 12 行** · `}`

右花括号终止匿名命名空间；短名仍可在本文件后续使用。若把范围一直包到 main，入口的放置就变了，不能把括号当随意缩进。

**第 13 行** · `auto ms_since = [](Clock::time_point t0) {`

匿名函数（lambda expression，现场定义的小函数对象）写作 [](...) {...}；空方括号表示不捕获外部局部变量。auto 让编译器推导对象类型，t0 是按值传入的时刻，外部起点不会被改。

**第 14 行** · `return std::chrono::duration<double, std::milli>(Clock::now() - t0).count();`

Clock::now() 取当前时刻，减起点得时长；`duration<double,std::milli>` 将计数的单位定为毫秒，count() 取数值。若直接取原时长的 count，单位未必是毫秒，标签相同也不能比较。

**拿数字验一下**：手边有秒表时可以对照：相差 0.125 秒的两个时刻，经这个 duration 转换后 count() 应是 125，而不是 0 或 125000。double 允许表达不足一毫秒的部分，后面 %.1f 只是显示时再舍入。

**第 15 行** · `};`

花括号结束函数体，分号结束第 13 行的变量定义。不要照普通函数定义的写法把分号省掉；这里保存的是可以在后面多次调用的对象。

**第 16 行**

空行把计时小工具与程序入口隔开。它不清空时钟，也不让任何变量改变。

**第 17 行** · `int main(int argc, char** argv) {`

main 是进程入口；argc 是参数个数，argv 是指向字符串指针的指针（pointer，保存地址的值）。例如 forest in out 一共三个参数，argv[0] 是程序名，两个路径从下标 1 取。

**第 18 行** · `auto t_all = Clock::now();`

用自动类型推导保存总起点。这个时刻后面不会重置，第 258 行用它算整次经过时间；若拿可重置的局部起点代替，total 只剩末阶段。

**第 19 行** · `auto t0 = Clock::now();`

再取一个独立起点，读文件从这里算。两个调用很接近但职责不同：第 225 行会复用 t0，不会影响总时钟。

**第 20 行**

空行将初始化与参数检查隔开；两个时钟继续计时，不存在隐式暂停。

**第 21 行** · `if (argc < 3) {`

条件语句 if 只在参数数目不足时进入。条件用小于而非等于，因为缺一个或两个路径都不允许；参数多于所需时源码并未拒绝。

**拿数字验一下**：把 argv 看成三格：格 0 是 forest，格 1 是 forest.in，格 2 是 forest.out。能访问下标 2 的条件是个数至少 3，因为编号从零开始。这与地图的内部行号从 1 开始完全是两套约定。

**第 22 行** · `std::cerr << "用法: " << argv[0] << " <输入文件> <输出文件>\n";`

标准错误流 cerr 的 << 是流插入，把用法、实际程序名、换行依次写给人看。这里的 << 不移动二进制位；输出目的地也不是 forest.out。

**第 23 行** · `return 1;`

return 1 从 main 提前返回非零状态，启动者可据此判断未成功。只打印提示不返回，下面仍会取不存在的路径。

**第 24 行** · `}`

此括号只结束参数不足分支。正常运行从这里往下走；不是所有路径都会在上面返回。

**第 25 行**

空行标志‘已具备访问两个文件名的条件’；它并不表示这两个路径一定可读可写。

**读代码前先排一条时间线。** 用三张纸分别写“名字”“起点”“时长”。在 forest.exe forest.in forest.out 里，名字那张纸上有三个字符串。程序读 t_all 的时候连输入能否打开都不知道，这时不能填写“读了几毫秒”。等到第 102 行，会发生的是拿新时刻减起点，不是从机器那里取一个叫 read 的硬件计数器。

|看到的拼法|在这个例子中问什么|不应据此推断什么|
|---|---|---|
|Clock::time_point|某个时刻在单调时钟上的位置|它是日历几点钟|
|Clock::now()−t0|两个时刻相隔多久|计数的一个单位一定是毫秒|
|`duration<double, std::milli>`(差).count()|把间隔以毫秒为单位读出|比显示的小数位更多就一定测得更准|
|return 1|这条启动请求因参数不足结束|任意一种参量错误都一定被这份程序发现|

**从零重写时怎么想**：先写出正常和异常两条路。正常：三个字符串齐全，去打开 argv[1]。异常：只有两个字符串，写用法并从 main 返回。让手指从两条路分别走一次，只有第一条能走到输入段。再把时钟放在两条路分开之前，你就知道为什么总起点早于真正文件读取。

**这段结束后的状态**：有效路径名已经可以取用，两个时刻已保存；输入文件尚未打开。

**写错会怎样**：参数数量把程序名也算进去。若用 argc<2，只有输入路径时仍会试图把缺失的输出路径当字符串。

**和前后版本的关系**：v1 也分阶段计时；v7 仍用普通进程入口，不会自动识别 MPI 进程编号。

**一句话记住**：看时钟先找起点，看参数先数程序名。

## 第 26–55 行 · 从文件读到一对指针

**这段在干什么**：把整份文本读进可连续访问的内存，再写一个按需取整数的小工具。设文件只有五个字符‘12 3\n’，游标指向 1 时第一次读取的结果应为 12，并停在空格上。

**代码块**：

```cpp
 26      // ==========================================
 27      // 1. 快速读入
 28      // ==========================================
 29      FILE* fp = std::fopen(argv[1], "rb");
 30      if (!fp) { std::fprintf(stderr, "open in failed: %s\n", argv[1]); return 1; }
 31  
 32      std::fseek(fp, 0, SEEK_END);
 33      long fsz = std::ftell(fp);
 34      std::fseek(fp, 0, SEEK_SET);
 35  
 36      std::vector<char> buf(fsz + 1);
 37      size_t got = std::fread(buf.data(), 1, fsz, fp);
 38      if (got != size_t(fsz)) {
 39          std::fprintf(stderr, "read failed: expected %ld bytes, got %zu\n", fsz, got);
 40          std::fclose(fp);
 41          return 1;
 42      }
 43      std::fclose(fp);
 44      buf[fsz] = '\0';
 45  
 46      const char* p = buf.data();
 47      const char* end = buf.data() + fsz;
 48  
 49      auto read_int = [&]() {
 50          while (p < end && (*p < '0' || *p > '9')) ++p;
 51          int v = 0;
 52          while (p < end && *p >= '0' && *p <= '9') { v = v * 10 + (*p - '0'); ++p; }
 53          return v;
 54      };
 55  
```

**逐行讲解**

**第 26–28 行**

三行纯注释用双斜杠标出输入阶段。它们帮助找位置，不会替程序打开文件或自动开始新的计时。

**第 29 行** · `FILE* fp = std::fopen(argv[1], "rb");`

文件指针 FILE* 接收 fopen(路径,模式) 的结果。rb 表示读已有文件并按二进制字节处理，在 Windows 上避免换行转换干扰文件长度。失败会返回空指针，不能接着读。

**第 30 行** · `if (!fp) { std::fprintf(stderr, "open in failed: %s\n", argv[1]); return 1; }`

逻辑非 !fp 检查打开失败。fprintf(stderr,格式,参数) 将路径代入 %s 并换行；随后退出让读者知道哪个输入路径有问题，不会误报成短读。

**第 31 行**

空行分开打开文件与测量长度；句柄 fp 在两段之间保持打开。

**第 32 行** · `std::fseek(fp, 0, SEEK_END);`

fseek 的三个参数是文件、偏移、基准；以 SEEK_END 为基准偏移零，定位到文件末端。这里只移动位置而不读数据；返回状态没有被检查。

**拿数字验一下**：位置图可画成‘开头 0 → 中间 1、2、3 → 末端 4’。四字节文件末端的位置是 4，不是末尾那个字节的编号 3。正因为这个差一，后面可以直接申请 fsz 个有效字符，而不用再给实际长度加一。

**第 33 行** · `long fsz = std::ftell(fp);`

ftell(fp) 查询当前文件位置并以 long 返回。此刻在末端，普通可定位二进制文件的位置才可用作字节长度。失败能返回负值，源码没有在分配前拦截。

**第 34 行** · `std::fseek(fp, 0, SEEK_SET);`

用 SEEK_SET 作基准、偏移 0，把位置移回开头；不回去会从末尾开始读，读不到刚量出的那些字节。

**第 35 行**

空行把测量位置与申请内存分离。fsz 的单位仍是字节，文件位置已经归零。

**第 36 行** · `std::vector<char> buf(fsz + 1);`

`vector<char>` 按 fsz+1 个字符分配连续空间。多出的一个位置用于第 44 行的零字符；不是说文件里还应该多读一个字节。

**第 37 行** · `size_t got = std::fread(buf.data(), 1, fsz, fp);`

fread(目的地址,每项字节数,项数,文件) 返回读到的完整项数。这里每项是 1 字节，所以 got 和文件长度可直接比较；buf.data() 是首元素地址，不是容器对象本身。

**拿数字验一下**：试读 5 项，结果返回 3，就只允许把前 3 项称为文件提供的数据。这也是为什么此处先比较 got，再向 buf[fsz] 写哨兵；写了哨兵不能让缺失的两个文件字节重新出现。

**第 38 行** · `if (got != size_t(fsz)) {`

把长度转成 size_t 再与实读量比较，意在发现短读。函数式转换 size_t(fsz) 不检查负数；测长本身仍有前提，不能拿类型统一当作输入检查。

**第 39 行** · `std::fprintf(stderr, "read failed: expected %ld bytes, got %zu\n", fsz, got);`

格式串的 %ld 匹配 long，%zu 匹配 size_t。把预期和实收的两个数都打印，能区分‘文件打不开’和‘打开后没读齐’。

**第 40 行** · `std::fclose(fp);`

短读路径在退出前 fclose(fp)，释放这个文件流。不能指望后面的正常关闭替它办事，因为下一行已经返回。

**第 41 行** · `return 1;`

此处返回失败，不拿部分文本当完整森林。少读的部分即便暂时碰巧是零，也不是用户提供的地图。

**第 42 行** · `}`

结束短读分支。成功路径从未走第 40 行，所以它还欠一次关闭文件的动作。

**第 43 行** · `std::fclose(fp);`

成功时关闭磁盘文件，之后扫描的是内存里的副本。关闭文件不会使 buf.data() 失效，因为容器拥有那段内存。

**第 44 行** · `buf[fsz] = '\0';`

写入空字符 '\0' 作尾部哨兵（sentinel，标记边界的特殊值），它与数字字符 '0' 不同。真实扫描仍用 p<end 保护，不能把这行误当成读取了一个空地格。

**第 45 行**

空行隔开‘把文件搬进来’与‘开始解释字符’。这以后不需要通过 fp 找格子了。

**第 46 行** · `const char* p = buf.data();`

const char* 是指向只读字符的指针：可移动游标 p，不能经 p 覆写字符。起点来自 data()；如果后来让容器重新分配，旧指针可能不再有效。

**第 47 行** · `const char* end = buf.data() + fsz;`

end 是首地址加真实字节长度，表示半开区间 [p,end) 的终点；此处刚好是哨兵位置。把它误设为末尾那个有效字符的地址，可能丢掉没有尾换行的末位数字。

**拿数字验一下**：若文本是 6 空格 1，内存有四个位置：0 是 '6'、1 是空格、2 是 '1'、3 是哨兵。数字 1 的地址小于 end，读完它正好等于 end。此时再读一次，返回零同时不前进，所以非法的缺字段需要调用者另行发现。

**第 48 行**

空行隔开游标和捕获这两个地址的小函数；不新建作用域。

**第 49 行** · `auto read_int = [&]() {`

[&] 按引用捕获（reference capture，通过原变量而非副本访问），无参数调用 read_int() 可移动外面的 p。若每次调用都从旧副本起读，n、m、t 无法依次消费。

**第 50 行** · `while (p < end && (*p < '0' || *p > '9')) ++p;`

while 只要条件为真就重复；&& 先验证范围再读 *p，|| 连接‘小于 0 字符或大于 9 字符’。++p 前进一个字节。它跳过所有非数字，不能用来正确解析负数。

**第 51 行** · `int v = 0;`

每调用一次就从 v=0 开始构造新整数。不能把上一个数字的结果留在 v 里，否则输入 12 空格 3 可能拼成 123。

**第 52 行** · `while (p < end && *p >= '0' && *p <= '9') { v = v * 10 + (*p - '0'); ++p; }`

只在范围内且属于数字时做 v=v×10+当前位，再移动指针。例如先见 1 再见 2 得 12。字符相减得到数值；没有检查过大的数字是否超出 int 可表示范围。

**拿数字验一下**：手算读入‘105 ’：v 从 0 变 1，再变 10、105；p 落在空格。中间数字 0 也必须使旧值乘 10，不是看见 0 就略过。文件里的空地字符和作为十进制数字的一位 0，是否独立成项取决于解析位置。

**第 53 行** · `return v;`

return v 把本次的数返回给调用者，p 则停在数字后的字符处。若本来就到了末尾，也会返回 0，调用者不能仅凭这个值区分缺字段和合法零。

**第 54 行** · `};`

结束 lambda 并用分号完成变量定义。此刻只是定义了解析器，真正的首次调用在第 59 行。

**第 55 行**

空行留给下一阶段标题。解析器及其引用仍在 main 作用域中有效。

**把游标的每一步画出来。** 把换行用“换”代替，纸上写五格：位置 0='1'、1='2'、2=空格、3='3'、4=换。位置 5 是哨兵而非文件内容。下表模拟两次 read_int；注意游标移动发生在函数体里，却能被下次调用看见，因为捕获的是原变量。

|动作|入口 p|v 的变化|退出 p|
|---|---:|---|---:|
|第一次跳过非数字|0|还没用 v；第一个字已是数字|0|
|第一次吃数字|0|0→1→12；看到空格停下|2|
|第二次跳过非数字|2|跨过一个空格，停在字符 3|3|
|第二次吃数字|3|0→3；看到换行停下|4|
|再调用一次|4|跨到 5，没有数字，仍得到 0|5|

**断点该放哪。** 若 n 正确而 m 也被读成 n，不要先怀疑森林逻辑。检查同一地址 p 在连续两次调用之间是否前进；若指针从未越过首位，会重复读，若一口气越过分隔符后的首位，则会吞掉下个字段的一部分。工程里一个“读数函数”其实同时间接返回两样东西：明面上的数，以及留给下一次调用的位置。

**这段结束后的状态**：文件已关闭；buf 仍然拥有文本。p 从首字节起步，end 永远停在有效区间之外的第一个位置。

**写错会怎样**：重复读文件并不修复游标错误；如果读了一个数却没移动 p，后面每次都会拿到同一份输入。

**和前后版本的关系**：v2 已经整块读取，但 v3 才检查 fread 的实际返回量。v8 在解析完事件后尝试归还这块内存。

**一句话记住**：读进多少字节，就只在多少字节的范围内解释字符。

## 第 56–84 行 · 把一格找回到两个位里

**这段在干什么**：输入把每格写成 0–3 的字符，这里改用两张位图回答‘树或火吗’和‘火或灰吗’。字有 64 位，位 0 对应该字里列号最小的格子。

**代码块**：

**逐行讲解**

**第 56–58 行**

三行注释切到位面初始化。它们没有改变 p，因此标题后的第一次取整数仍从文件头开始。

**第 59 行** · `int n = read_int(), m = read_int(), t = read_int();`

顺序读三个整数：n 管行列、m 管事件、t 管模拟步数。三者不能互换；m=1、t=4 就是一张事件单推动四轮，而不是四张单只算一轮。

**第 60 行** · `int W = (n + 63) >> 6;`

W 按每行算字数。(n+63)>>6 在本题非负且加法可表示时等于向上取整的 n/64；65 列要两个字，不能只给整除得到的一个。

**拿数字验一下**：各看三个邻近尺寸：n=63 时 W=1，n=64 时 W=1，n=65 时 W=2。若先做 n/64 再无条件加 1，在 n=64 时白留整整一字；若只做 n/64，在 63 和 65 时又会少分配。

**第 61 行** · `size_t total_words = size_t(n + 2) * W;`

分配 (n+2) 行，每行 W 字，真实行在 1..n。先把行数转成 size_t 再做乘法，减少 int 中间乘积过小的风险；n+2 自身仍按 int 算。

**第 62 行**

空行分开尺寸推算与容器分配。total_words 数的是字，不是字节；下一行的每个元素有 8 字节。

**第 63 行** · `std::vector<uint64_t> b1(total_words, 0), b0(total_words, 0);`

每代两张位面：b1 标‘树或火’，b0 标‘火或灰’。构造参数 (个数,初值) 给每一字填 0。零既编码空地，也让从未写过的边界和填充位保持无火。

**拿数字验一下**：拿八个输入格 0 1 2 3 1 0 2 0 缩小演算。把第 0 列写在纸最右端，b1 是 01010110，b0 是 01001100。把这两串与起来得到 01000100，只有位 2 和 6 是火，和输入中两个 2 对上。

**第 64 行** · `std::vector<uint64_t> nb1(total_words, 0), nb0(total_words, 0);`

nb1、nb0 与当前面同尺寸，但属于下一代。若直接把结果写回 b1、b0，后算的行可能偷看到本步刚生成的新火，破坏同时更新。

**第 65 行**

空行隔开储存空间和编码规则。名字 nb1 中的 n 指下一代，不是地图边长。

**第 66 行** · `const uint64_t b1bit[4] = {0, 1, 1, 0};`

常量查找表（lookup table，用整数下标直接取得预先写好的答案）列出四种输入的高位。原始值 1、2 查得 1，树与火同属 b1，不能简单拿输入值的二进制高位代替。

**拿数字验一下**：一张查表写在纸上：输入值 → 高面回答：0→否、1→是、2→是、3→否。‘高面’只是我在这张卡上给 b1 的位置，不能推出题面数字 1 的高二进制位也是 1。要先约定编码，再对外输出。

**第 67 行** · `const uint64_t b0bit[4] = {0, 0, 1, 1};`

第二张表只给输入 2、3 返回 1。和上一行合起来按 b1b0 顺序是 00、10、11、01；这个顺序与 br 的数值二进制并不相同。

**第 68 行**

空行隔开两张编码表与实际格子读取。此时四张图上仍然都是零。

**第 69 行** · `for (int i = 1; i <= n; ++i) {`

外层循环从内部行号 1 走到 n（含 n）。上下各留一行；如果照列那样从 0 写，第一行会落在原本预留的边界位置。

**第 70 行** · `size_t row_offset = size_t(i) * W;`

行首偏移是 i×W 字。把行号转换后再乘，以 65 列为例 W=2，内部第 2 行首字下标为 4。这里不是 i×n 个格子。

**第 71 行** · `for (int j = 0; j < n; ++j) {`

列号 j 从 0 到 n−1，一开始就对应实际的位编号。存储没有给每一行的左边预留一个位；和第 69 行同样加 1 就会把第 63 列塞进下一字。

**第 72 行** · `while (p < end && *p < '0') ++p;`

对合法地图字符只需跳过小于 '0' 的空格或换行。条件先检查 end 才解引用；它不是全字符合法性验证，字母和 '9' 也不会在此被筛掉。

**第 73 行** · `if (p >= end) { std::fprintf(stderr, "input truncated\n"); return 1; }`

在解引用前检查 p 是否已经到末端；若格子还没数完，报告文本截断并退出。这个检查不判断字符是不是题目允许的四种状态。

**第 74 行** · `int v = *p - '0';`

把一个数字字符与 '0' 相减得到状态。例如 '3'−'0'=3。这里一次仅取一个字符，不能照第 52 行的十进制多位解析方式跨格消费。

**第 75 行** · `if (v > 0) {`

非空状态才需设位，因为容器初始为零。这个分支省了空地的两次查表，不能把 v>0 误读成‘v 已在 1 到 3 之间’。

**第 76 行** · `size_t idx = row_offset + (size_t(j) >> 6);`

全局字下标＝行首＋列号整除 64。列 63 仍在本行第一字，列 64 才在第二字；同一字中不同格靠下一行的 bit 区分。

**拿数字验一下**：给 n=65、i=2、j=64，row_offset=4，idx=5，bit=1。两张面都在各自数组的第 5 号字取最低位。换成 j=63，idx=4，bit=1ULL<<63；格子只差一列，字地址和位编号却同时改变。

**第 77 行** · `uint64_t bit = 1ULL << (j & 63);`

1ULL 是无符号长长整数字面量，左移 j&63 位形成单一置位掩码。列 64 的低六位是 0，不会出现移位量 64；若用窄的整数 1，高位列便可能出错。

**第 78 行** · `if (b1bit[v]) b1[idx] |= bit;`

若高位表在 v 项为真，就对目标字做按位或赋值 |=。只置 bit 对应的一格，不会擦除同一字里先前读过的 63 格；普通赋值 = 则会。

**第 79 行** · `if (b0bit[v]) b0[idx] |= bit;`

低位独立查询并置位。火要同时设置两面，所以两个 if 不能接成 else if，不然输入 2 被误码成树。

**第 80 行** · `}`

结束‘非空才写’分支。不要把移动 p 的语句也一起包进去：遇到空地时同样必须读掉这个字符。

**第 81 行** · `++p;`

前进一步的是字符指针 p 而非列号 j。哪怕本格是空地也要消耗字符；否则后面的循环虽按时结束，却会反复读取同一空地，把后续输入整体错位。

**第 82 行** · `}`

结束一行的列循环。列号在下一次外循环会从零重新开始，指针 p 却继续沿整个文件向前，不需要人为跳过固定长度的一行。

**第 83 行** · `}`

结束输入地图的行循环。这里恰好完成 n² 次格子读取，新图没有被写过；接下来的数字属于事件，不应再当状态处理。

**第 84 行**

空行标出从固定二维形状的格子区切到可变长度的事件区。游标会由通用整数解析器继续使用。

**把地图格刻成地址卡。** 取 n=65，每行 W=2。设输入零基行 0 的第 0 列是树、63 列是火、64 列是灰，其他都空。请分别列出键 (内部行、字下标、位号、b1、b0)，再看表。

|输入坐标|内部行|全局字下标|位号|这一位写成 b1b0|
|---|---:|---:|---:|---|
|(0,0)|1|2|0|10|
|(0,63)|1|2|63|11|
|(0,64)|1|3|0|01|
|(1,0)，假设为空|2|4|0|00|

下标 2 的高面有位 0 与位 63，低面只有位 63；下标 3 的低面仅位 0。其余 63 个未用位虽然分配了，却不对应真格。初始为零，转移里的 burn 必须由 tree 筛选，而填充位不可能是 tree，所以水平移位偶尔把候选邻火移进去也不会凭空长树。这个推理比直接说“补齐总没事”更可靠。

**逆向自查**：若只知道一个全局字下标 3，你无法确定唯一一棵树；还需要字内位。反之拿到位号 0，也可能是每行的第 0、64、128 列。程序里 idx 与 bit 总成对出现，正是因为地址里有两个层次。

**这段结束后的状态**：b1/b0 是初态；nb1/nb0 和两端哨兵行仍全零。p 位于格子区末格之后，可以接着读事件。

**写错会怎样**：全图一起向上取整不等于每行单独取整。以 n=65 为例，每行需要两个字，第二个字只用一位；下一行必须从新的两个字起步。

**和前后版本的关系**：v3 一格占一个字节、四侧留边；v4 以后行列的边界处理不再对称。br 的两位含义另外定义。

**一句话记住**：行找字，列找位，编码表决定该置哪一面。

**逐行讲解**

**第 85 行** · `struct magic_event {`

结构体（structure，把有关字段组成一种新类型）在 main 内定义，名字为 magic_event。单纯定义结构不会创建 m 个对象，实际存储在第 90 行才申请。

**第 86 行** · `int time, type;`

两个 int 分别表示时间与类型。它们虽然同类型却回答不同问题：时间决定何时消费，类型决定本行还要取几个参数。

**第 87 行** · `int para1[2]{};`

固定长度数组 int para1[2]{} 给惊雷预留行列两个整数，花括号把元素初始化为零。数组本身不记当前事件种类，必须配合 type 读取。

**拿数字验一下**：惊雷在文件里为‘4 1 4 5’，存后 time=4、type=1、para1={4,5}，para2 仍为四个零。后续读取哪组参数必须看 type，而不能试图以‘这一组有没有零’辨别，因为 (0,0) 完全是合法坐标。

**第 88 行** · `int para2[4]{};`

给矩形预留四个端点，之后按起始行、起始列、终止行、终止列解释。把四个数当成起点和宽高会多选或少选一整片。

**第 89 行** · `};`

花括号合上类型定义，分号不可像普通控制块那样省略。这行后面可以用 magic_event 声明对象，但还没填过任何一次事件。

**第 90 行** · `std::vector<magic_event> magic(m);`

`vector<magic_event>` magic(m) 建立 m 个可下标访问的事件对象。用 reserve(m) 只留容量而不产生元素，不能替代此处的按下标填写。

**第 91 行** · `for(int i = 0; i < m; i++) {`

for 的三段为初始化、继续条件、每轮更新。i++ 在循环尾递增，不在此处使用旧值；有效下标从 0 到 m−1，m 为 0 时整个循环不进入。

**第 92 行** · `magic[i].time = read_int();`

以 magic[i].time 访问第 i 张事件单的时间成员。read_int 会越过前一次留下的空白；若重复使用旧时间而不读，游标和事件内容都会错。

**第 93 行** · `magic[i].type = read_int();`

下一整数是 type，和前一个时间必须分两次读取。比如输入‘4 1 4 5’，两个 4 的含义分别是时间、行，不能只靠数值认字段。

**第 94 行** · `if(magic[i].type == 1) {`

类型等于 1 时才把本条余下两字段当点坐标。== 作相等判断；赋值运算 = 会改变字段，不能替换这个比较。

**第 95 行** · `for(int j = 0; j < 2; j++) magic[i].para1[j] = read_int();`

不带花括号的 for 只反复执行紧跟的赋值语句，j 取 0、1，依次保存 x、y。读一个就停会把 y 留给下一张事件单。

**第 96 行** · `}`

结束惊雷的读取支路。类型 2 并不进入它，因此游标仍指向矩形的第一个整数，下一支才能读全四个端点。

**第 97 行** · `if(magic[i].type == 2) {`

第二个独立 if 检查回春。合法类型只有 1、2，两次判断只会命中一次；程序未另设非法类型的报错路径。

**第 98 行** · `for(int j = 0; j < 4; j++) magic[i].para2[j] = read_int();`

j=0..3，读四次整数写进 para2。这里的 4 是每个矩形所需坐标的个数，和事件总数 m 无关；端点顺序决定后面循环的方向。

**第 99 行** · `}`

退出类型 2 的参数读取块。此刻这张事件单的游标已经越过全部有效数字，下一个空格或换行留给 read_int 跳过。

**第 100 行** · `}`

结束 m 次装入。事件仍按文件顺序保存，代码没有排序；第 131 行以后能够只带一个游标，依赖题面已给的升序保证。

**第 101 行**

空行把读取和统计分开。文件实际上早在第 43 行关闭，但读阶段还包含了内存里的解析和格式转换。

**第 102 行** · `double ms_read = ms_since(t0);`

ms_since(t0) 的 double 返回值记录读取阶段毫秒数。它包含读取、分配和编解码，不是磁盘带宽的纯测量；以后重用 t0 不改变这个已存的值。

**拿数字验一下**：要估 IO 是否值得优化，先记下这段包含的项目：打开与测量、整段读入、向量分配、逐格编码、读事件。换硬盘只能直接影响其中一部分；读段耗时减半也不能反推出磁盘读速恰好翻倍。

**第 103 行**

空行切换到主模拟；也提醒读者 ms_read 不会在每个时间步重新累计。

**第 104–106 行**

三行注释给主循环命名；它描述接下来一整段，不是‘从此刻起自动并行’。真正的并行指令在第 111 行。

**第 107 行** · `double ms_event = 0, ms_move = 0;`

两个 double 累计器初始化为 0。一个累计事件阶段，一个累计转移阶段；写成只声明不赋初值再用 += 就无法从可预期的计数起跑。

**第 108 行** · `int cnt_event = 0;`

cnt_event 是共享的‘下一张待消费事件单’的下标，不是当前时间。没有事件的时间步也要做转移，却不应让这个下标加一。

**拿数字验一下**：事件时间若是 2、5、9，ts=3 时游标为 1，指向时间 5；ts=4 时仍为 1。ts 每拍走一步，cnt_event 只在消费时走一步。两者碰巧数值相等没有任何特殊含义。

**第 109 行** · `auto t_step = Clock::now();`

把 t_step 定成时钟的时间点，在团队外声明使后面两个 single 看的是同一个对象。第 129、164 行才设置各阶段使用的真正起点。

**第 110 行**

空行隔开共享量和团队内部私有量。变量属于哪里由声明位置和并行规则决定，不由空行或名字决定。

**用三张事件单验证输入没有串栏。** 假设头信息的 m=3、t=5，事件依次是下面三行。先不碰地图，只读记录，把每个数字写到指定成员中；表里不填的字段是另一类事件用的预留空间。

|输入事件行|time、type|生效参数|读完后指向|
|---|---|---|---|
|1 1 0 3|1、1|para1=(0,3)|下一张单的时间 3 之前的空白|
|3 2 0 1 2 4|3、2|para2=(0,1,2,4)|下一张单的时间 5 之前的空白|
|5 1 2 0|5、1|para1=(2,0)|有效数据末端或尾部空白|

现在遮住输入只用事件表来走五轮。第 1 步消费第 0 张单，游标变 1；第 2 步不消费，游标仍 1；第 3 步消费第 1 张，变 2；第 4 步仍 2；第 5 步变 3。末轮再进 while 时，cnt_event<m 为假，代码不应访问 magic[3]。同一个例子能分别检查读阶段的字段长度和算阶段的游标边界。

**从零重写时怎么想**：先决定数据在什么时候才完整。末尾那个矩形参数未读取之前，不能把读时钟停掉；否则 v1 与 v7 同样的 read 标签就可能一个包含所有事件、另一个只包含格子。

**这段结束后的状态**：m 张事件单就绪，cnt_event 指向第一张尚未消费的单，读取耗时已有记录。

**写错会怎样**：如果矩形只取两个参数，两个剩余数字会被误认作下张单的时间和类型。程序未必报错，模拟却会从那一刻开始跑偏。

**和前后版本的关系**：v1–v7 使用相似事件结构；v8 把端点取了名字。br 选择按步号直接查表。

**一句话记住**：事件条数、坐标个数和模拟步数分开数。

## 第 111–140 行 · 按行分工，派一个人放惊雷

**这段在干什么**：一队线程各有私人的行段和窗口，却共享同一份森林和事件进度。例：n=10，三个线程，分块长度 4，真行分别是 1–4、5–8、9–10。

**逐行讲解**

**第 111 行** · `#pragma omp parallel`

预处理指令 #pragma 给编译器附加指示；omp parallel 让团队中的各线程执行随后的结构块。若未启用，对普通循环不能凭这行自动获得多线程；显式运行库调用另有链接要求。

**第 112 行** · `{`

左花括号给并行指令划定作用范围。每个参与者都进入同样的代码，下一行读到的线程数相同，编号则各不相同。

**第 113 行** · `int num_threads = omp_get_num_threads();`

omp_get_num_threads() 无参数，返回当前团队真实线程数，不是整机核数。算行段要用实际参与者：按设想的 16 人分，实际 4 人到场就会有行没做。

**第 114 行** · `int tid = omp_get_thread_num();`

omp_get_thread_num() 返回团队内从 0 开始的编号。它用于分配行段，不是操作系统进程号，也不等于这次 single 的执行者。

**第 115 行**

空行分开‘知道我是谁’和‘计算我负责哪些行’。这些局部变量在线程间各有一份，不需要上锁读取编号。

**第 116 行** · `int chunk = (n + num_threads - 1) / num_threads;`

对正数做向上取整除法。n=10、团队=3，则 (10+2)/3 为 4，每人最多四行。改为直接整除得 3，三人总计只能覆盖九行。

**拿数字验一下**：n=17、T=4 时 chunk=5，各段为 1..5、6..10、11..15、16..17。一段行数差三行，这是向上取整统一块长的结果，不保证行数差最多一。若末段太短，前面线程仍必须在发布前做完。

**第 117 行** · `int start_r = tid * chunk + 1;`

起点 tid×chunk+1 把分段编号转成内部一基行号。tid=0 从 1 起，tid=1 从 5 起；省略 +1 会把第 0 行哨兵当真行。

**第 118 行** · `int end_r = std::min(n, (tid + 1) * chunk);`

std::min(a,b) 返回较小者，把末段截在真行 n。三人分十行时第三段理论到 12，必须截到 10。人比行多时，起点可能大于终点，第 169 行处理。

**第 119 行**

空行把行段上下界和私有的三行缓冲分开。end_r 是闭区间端点，循环会处理编号等于它的那一行。

**第 120 行** · `std::vector<uint64_t> f_prev(W, 0);`

每个线程建立长 W 的前一行火图。这里 W 的单位为 64 位字，不是格子数；一条 16384 列的行只用 256 个字。

**第 121 行** · `std::vector<uint64_t> f_curr(W, 0);`

f_curr 保存当前行哪些格为火，而不是该行所有状态。只拿它无法区分树与灰，判断树时仍必须回到 b1/b0。

**第 122 行** · `std::vector<uint64_t> f_next(W, 0);`

f_next 是下一行的旧火缓冲，不是下一代的森林。字母 next 在 f_next 里指空间方向，在 nb1 里指时间方向，混淆会引入提前传播。

**第 123 行**

空行结束团队的一次性准备。从下一行起反复使用已分配的三个容器，不是每个时间步都重新申请三次。

**第 124 行** · `for (int ts = 1; ts <= t; ++ts) {`

时间步从 1 到 t 且两端都含。每个线程都要经历同样的步数与栅栏顺序；不能让空行段线程自行提前返回，否则别人可能一直等待。

**第 125 行**

空行分隔循环头与事件阶段。没有事件的时间步也要进入下面的同步区，不能跳过整轮。

**第 126 行**

纯注释说本阶段串行，意思是一次由团队中一人改共享状态，而不是整个程序终止并行区、销毁所有线程。

**第 127 行** · `#pragma omp single`

single 指令从团队中选一人执行接下来的块。没有 nowait 时，末尾有隐式栅栏；它不规定进入块前大家已到齐，也不指定是哪位线程执行。

**拿数字验一下**：把团队想成三人共看一张事件单：抽到的人执行，另两人从块尾等待。不能推断下一时间步还会抽到同一个人，因此不能把共享事件进度放进某个线程的私有局部变量里，然后指望所有单都被它依次消费。

**第 128 行** · `{`

这对花括号的左端圈出单人工作的范围，直到第 165 行才结束。若只把计时语句圈进去，后面的事件循环就会被每个线程执行。

**第 129 行** · `t_step = Clock::now();`

选中的线程用 Clock::now() 重置事件阶段起点。计时点属于共享变量；只有一位写，其他人在这段不会读写它。

**第 130 行**

空行分开计时起点和事件消费。已有的等待或进并行区的成本不自动计入此次事件循环。

**第 131 行** · `while (cnt_event < m && magic[cnt_event].time <= ts) {`

先用 cnt_event<m 排除没有单子，再读其 time。&& 的短路性保护数组尾；用 <= 会消费已经到期的单，但看不到当前未来单子后面被错排的早单。

**拿数字验一下**：拿合法时间 1、4、8 作例，ts=4 时循环消费时间 4，下一次检查时间 8 便停。若文件错排为 8、4，ts=4 时游标面对 8，不会主动越过它去取后面的 4。所以‘小于等于’只是一种容忍，不能替代排序。

**第 132 行** · `if(magic[cnt_event].type == 1) {`

检查本张单是不是惊雷。魔法只会对旧图做就地修改；若写到下一代，稍后的转移会盖掉魔法，邻居也看不到刚点燃的火。

**第 133 行** · `int x = magic[cnt_event].para1[0] + 1;`

取点的原始行并加一，得到内部真行号 x。输入 (0,0) 对应内部第 1 行；这一次平移绝不是‘向下一个邻居传播’。

**第 134 行** · `int y = magic[cnt_event].para1[1] + 1;`

列先也被写成一基 y，这是沿用早期版本的写法。留意下一行随即减回来；位列真正用的是零基下标。

**第 135 行** · `int c = y - 1;`

c=y−1 把列还原到 0..n−1。拿 y 直接算掩码，会把每一列的火向右挪一格；最右端可能落入补齐位或邻行。

**第 136 行** · `size_t idx = size_t(x) * W + (size_t(c) >> 6);`

把一基行号乘 W，加上零基列号除以 64 得到字下标。例：n=65 时 W=2，原始第 0 行第 64 列在内部下标 3，不是 64。

**第 137 行** · `uint64_t bit = 1ULL << (c & 63);`

用 c&63 取字内位置并形成一个仅一位为 1 的掩码。如果整字都置位，一次惊雷就可能同时点到一整排的树。

**第 138 行** · `if ((b1[idx] & bit) && !(b0[idx] & bit)) b0[idx] |= bit;`

两次按位与测试同一位，高面有而低面无才是树。逻辑 && 与 ! 把两次测试化成一个真假结论；对低面做或赋值使 10→11，灰和空都不变。

**拿数字验一下**：玩具字的 b1=00101100、b0=00001000。惊雷点位 2：高面该位 1、低面 0，低面变成 00001100；若点位 3，高低原本皆为 1，属于已着火，不能改变。不要对整字做 b1!=0 && b0==0 来代替逐位测试。

**第 139 行** · `}`

结束惊雷分支。下一行的 else if 和第 132 行的 if 配对；不能把它接到内层单行的树判定上，否则事件分类就变了。

**第 140 行** · `else if(magic[cnt_event].type == 2) {`

若前一类型判断未命中，才检查是否为回春。接下来要处理的是闭矩形，不再把两个坐标当一个点；不合法的类型没有实现第三种语义。

**每个变量是谁的。** 把一支队伍看作多人围着同一张桌子。桌面放整图和事件进度，每人手边放自己的行号和草稿。‘只读’和‘私有’不是同义：同一张旧图可以同时被许多人读取，仍是共享对象。

|变量|有几份|这个阶段允许谁改|如果放错地方|
|---|---|---|---|
|b1、b0|团队一份|事件 single 中被选的一人|每人私有会看见不同森林|
|cnt_event|团队一份|事件 single 的执行者|若私有且 single 换人，事件进度发生分歧|
|tid、start_r、end_r|每人一份|各自初始化|若共享，线程可能覆盖别人的行段|
|f_prev、f_curr、f_next|每人三行|本线程|若共享，人走不同行会覆盖窗口|
|nb1、nb0|团队一份|每人只写自己的真行|按行独占写才能在发布后组成全图|

**独立推算一个极端**：n=2、团队=5，chunk=1。tid=0、1 有效；其余三个起点为 3、4、5，终点都被截成 2。可以猜到它们不参加行循环，但不能猜它们不进入 single 或 barrier。某个没有真行的人同样可能被选去放惊雷；放惊雷使用的是全图坐标，与它自己的 start_r 无关。

**这段结束后的状态**：分工已定；进入类型 1 分支时，目标树按两位编码被点燃。若类型是 2，控制流进入下一段。

**写错会怎样**：线程编号不是行号。每人拿不到整除时剩下的行就会漏算；反过来把事件也让每人做一遍，既会争用写入又会移乱游标。

**和前后版本的关系**：v6 使用运行库调度循环；v7 自己算固定行段。v8 的惊雷明确交给线程 0，v7 的 single 不指定编号。

**一句话记住**：谁分到哪些行，与谁执行一次事件是两件事。

## 第 141–168 行 · 只让矩形里的灰复活

**这段在干什么**：复活一个区间不是把整个字都设成树。先取出本字与矩形的交集，再从其中挑出旧灰。跨字例：列 62–65 分别选中字 0 的 62、63 和字 1 的 0、1。

**逐行讲解**

**第 141 行** · `int sx = magic[cnt_event].para2[0] + 1, sy = magic[cnt_event].para2[1] + 1;`

同时取开始行 sx 与开始列 sy，两者先加一。逗号分隔的是同一 int 声明中的两个变量，不是一个坐标对象；矩形坐标顺序与输入一致。

**第 142 行** · `int ex = magic[cnt_event].para2[2] + 1, ey = magic[cnt_event].para2[3] + 1;`

同样得到终止行和终止列。终点是包括在内的，不是数组半开区间的尾指针；面积为 (ex−sx+1)×(ey−sy+1)。

**第 143 行** · `int c_sy = sy - 1, c_ey = ey - 1;`

两个列端点减一还原零基位列，行端点保持一基。以后处理跨字区间，只有这两个零基列适合用低六位取余。

**第 144 行** · `int j_start = c_sy >> 6, j_end = c_ey >> 6;`

两端各自右移六位，得到首字和末字的编号。列 62..65 的结果为 0..1，两个字都要动；用长度除 64 会错过这个四格跨字例。

**第 145 行**

空行分开算一次的范围与逐行执行的部分。行数不同不会改变这两个列端点所在的字编号。

**第 146 行** · `for (int r = sx; r <= ex; ++r) {`

逐行 r=sx..ex，等号保证仅一行高的矩形也执行一次。这里位于 single 内，不会由多个线程同时去改同一矩形。

**第 147 行** · `size_t row_offset = size_t(r) * W;`

每换一行重新算行首字偏移。矩形覆盖同样列号但不同行时，绝对下标要相差 W 字；忽略这一项只会反复改同一行。

**第 148 行** · `for (int j = j_start; j <= j_end; ++j) {`

在这一行里逐字走到末字，j 在这里是字编号而非列号。每次可以同时决定最多 64 格中哪些灰复活。

**第 149 行** · `int lo = (j == j_start) ? (c_sy & 63) : 0;`

条件运算符 ?: 按真假二选一：首字左端从 c_sy 对 64 的余数开始，后续字从位 0 开始。若所有字都用原始左端余数，中间字会漏掉前缀。

**拿数字验一下**：同一行受选列 62、63、64、65。走到 j=0，lo=62，hi=63，低 62 位全要原样保留；走到 j=1，lo=0，hi=1，剩余高 62 位保持。这是一个矩形，不是要对两个完整字都执行回春。

**第 150 行** · `int hi = (j == j_end) ? (c_ey & 63) : 63;`

若当前是末字，右端是 c_ey 的余数，否则可以到位 63。一字内的短矩形同时是首字和末字，两行判断都得生效。

**第 151 行** · `uint64_t mask = (lo == 0 && hi == 63) ? ~0ULL : (((1ULL << (hi - lo + 1)) - 1) << lo);`

覆盖 0..63 时取无符号零逐位取反 ~0ULL，得到全 1。其余长度 k=hi−lo+1 小于 64，(1ULL<<k)−1 先造 k 个低位 1，再左移 lo。比如位 2..4 得 00011100；两端不能少算一个。

**拿数字验一下**：单点区间 lo=hi=3 时，宽度是 1，低位掩码为 1，移到位 3 得 00001000。若把 hi−lo+1 漏写 +1，单点矩形的掩码为零，肉眼看大矩形未必发现这个错误；单格例最好记。

**第 152 行** · `size_t idx = row_offset + j;`

将本行起点与当前字编号相加。这里 j 已经是字编号，不应该像第 76 行的格子列那样再除一次 64。

**第 153 行** · `uint64_t ash = mask & b0[idx] & ~b1[idx];`

按位与依次保留矩形掩码内、低面为 1、高面为 0 的格子。这才是旧灰位集合 ash；若少了 ~b1，旧火也会被误当成灰复活。

**第 154 行** · `b1[idx] |= ash;`

按位或赋值给高面，只把 ash 选中的位置从 0 变为 1。注意要沿用上一行保存的 ash，不能在改完高面后再以新高面重新选灰。

**第 155 行** · `b0[idx] &= ~ash;`

低面与 ash 的按位补集，清掉同一组位置的低位，别的位置不动。与前一行合起来实现 01→10；只做前一行会把灰变为 11 即火。

**拿数字验一下**：玩具掩码已筛出 ash=00010010。这两个位置原本高 0、低 1；高面 |=ash 先变成两位都是 1，然后低面 &=~ash 只在这些位置清零。中间一瞬间的 11 不是一个新的时间步，其他线程到第 165 行后才利用完成的魔法。

**第 156 行** · `}`

结束当前行的字循环。到了这一点，矩形这一行的首尾残字和中间整字都已处理；行循环仍可能有下一行。

**第 157 行** · `}`

结束矩形的行循环。此时不必再扫描矩形外的区域：逐字合并已经保存了掩码外原有两位。

**第 158 行** · `}`

结束类型 2 的处理块。接下来的事件进度要在类型判断之外更新，否则只遇到惊雷时可能忘记消费。

**第 159 行** · `cnt_event++;`

后置 ++ 把共享游标移向下一张单，这里的旧值没有被使用。若遗漏，while 条件一直盯同一条到期事件，步号就推进不了。

**第 160 行** · `}`

退出所有到期单子的 while 循环。要么单子已经用完，要么下一张是未来的；不能把循环结束误当成所有时间步都结束了。

**第 161 行** · `ms_event += ms_since(t_step);`

毫秒累加器 += 把本次事件段加到旧总量中。无事件时也会有检查与计时开销。它不表示所有核在魔法阶段花费的处理器时间之和。

**第 162 行**

空行分隔累计事件耗时与重启转移计时。两个阶段共用 t_step 变量，但记录的起点并不相同。

**第 163 行**

这行注释提示为什么要重设起点：若从处理魔法之前开始算 move，同一段工作会同时进入两个指标。v6 第 166 行已有相同操作。

**第 164 行** · `t_step = Clock::now();`

给共享时刻重新赋值。转移的读数会包进离开 single、等待其他线程、交换结果等成本，不是只计内层几个位运算的纯耗时。

**第 165 行** · `}`

**第 166 行**

**第 167 行**

**第 168 行**

纯注释指明进入并行转移。不是每一行都有独立线程；下面每名线程自行走其固定行段，行段之间可以同时进行。

**一张矩形掩码的账。** 为了在纸上画满一字，用八位玩具字。假设当前 b1=01011000，b0=00111010，回春只覆盖位 1..4，即 mask=00011110。从右往左数位 0..7。不要先改图再找灰，那会把证据改掉。

|---|---|---|
|~b1（只看这八位）|10100111|旧高面为零的候选|
|b0 与 ~b1|00100010|旧灰在位 5 与位 1|
|再与 mask|00000010|只复活位 1；位 5 在矩形外|
|新 b1|01011010|在位 1 设高位|
|新 b0|00111000|在位 1 清低位|

如果把第 154、155 行分别看成两条独立魔法，很容易误以为中间新出现了火。实际上 ash 取自同一份旧状态，两次写共同实现一次状态修改；其间没有任何线程应该启动状态转移。回到 64 位版本再检查一个整字矩形：lo=0、hi=63，计算长度 64 的普通分支不执行；取全 1 不是微优化，而是避免无效移位的语义必要条件。

**遮住源码重写**：先写出“只改变谁”的布尔条件，再写“该状态的两位由几变几”。不先求出共同的 ash，后面想分别修改两面时很难保住‘选的还是同一批格子’。

**这段结束后的状态**：本步魔法的全部写入已结束。工作组通过 single 末端同步后才读邻居；t_step 指向转移阶段的起点。

**写错会怎样**：把 1 移 64 位不是得到一个‘第 65 位’；对 64 位操作数，这种移位未定义。整字覆盖必须另走全 1 掩码分支。

**和前后版本的关系**：v4 已处理整字特例；v6 的计时起点也已经重置。v8 的主要变化是矩形的各行可由不同线程负责。

**一句话记住**：先挑出矩形里的旧灰，再同时改它的两面。

## 第 169–188 行 · 启动窗口：分界不是森林边缘

**逐行讲解**

**第 169 行** · `if (start_r <= end_r) {`

只让确有真行的线程初始化和计算窗口。若 n 小于线程数，start_r 可能大于 end_r；空闲者跳过计算，却不能跳过第 209 行的共同等待。

**第 170 行** · `if (start_r > 1) {`

如果自己的首行大于 1，则有真实上邻。这里比较的是全图首行，不是问‘我是不是自己行段的第一行’，后者对每个线程总为真。

**第 171 行** · `size_t offset = size_t(start_r - 1) * W;`

取 start_r−1 的行首字偏移，读取的是别的行段也可能负责的旧图区域。只要大家都不改旧图，这种共享只读访问不需要给每个字加锁。

**第 172 行** · `for(int j = 0; j < W; ++j) f_prev[j] = b1[offset + j] & b0[offset + j];`

遍历这一行的 W 个字，对高、低面逐位取交集。11 才是火，所以 f_prev[j] 存的每一位是在回答上一行该列‘是否有火’，而不是原来的状态数字。

**拿数字验一下**：若第 4 行的两面分别是 01010110、01001100，则 f_prev=01000100。对第 5 行来说，它表示第 2 列和第 6 列各有一个来自正上方的火源。行方向不用移位，因为同一列的位编号没有变化。

**第 173 行** · `} else {`

else 接住全图第一行的情况。即使有人调整了线程数，这个分支仍只表示没有上邻，不表示没有上一位线程。

**第 174 行** · `std::fill(f_prev.begin(), f_prev.end(), 0);`

fill(起迭代器,尾迭代器,值) 用 0 覆盖整个前行缓冲；迭代器是用来走容器位置的对象，end 不包含在区间内。复用窗口时不能只依赖初始为零。

**第 175 行** · `}`

合上初始化上一行的分支。无论走哪条路，f_prev 的每一字都已经定义，后面的无条件四邻或运算才有同一含义。

**第 176 行**

空行转向当前行的初始化。上边缘可填零，但当前行一定是真行，因为第 169 行已过滤掉空行段。

**第 177 行** · `size_t offset = size_t(start_r) * W;`

计算本线程第一条真行的旧图偏移。这里的 offset 与第 171 行的同名局部变量不冲突，前者所在的 if 块已结束。

**第 178 行** · `for(int j = 0; j < W; ++j) f_curr[j] = b1[offset + j] & b0[offset + j];`

将本段第一行解码为火位填入 f_curr。若错误地直接把 b1 放进去，所有树也会变成邻火来源，森林一拍就会异常扩散。

**第 179 行**

空行切开只在行段开头做一次的装载和即将重复的滚动。每行都重建三个数组虽可能算对，却失去窗口的复用意义。

**第 180 行** · `for (int r = start_r; r <= end_r; ++r) {`

行 r 从段首走到段末，每次向下移动一行。上下界包括在内；其他线程也在做同样的循环，但它们写的是不相交的行。

**第 181 行** · `if (r < n) {`

只要不是全图末行，就有真实下邻。假设本段到 8、全图到 10，算 8 时仍得读 9；用 end_r 作判断会在第 8 行造出假边界。

**第 182 行** · `size_t next_offset = size_t(r + 1) * W;`

用 r+1 乘 W 得到下一行在旧面中的位置。若移到 r−1，此处会把上邻装两遍并永久漏掉下邻。

**第 183 行** · `for(int j = 0; j < W; ++j) f_next[j] = b1[next_offset + j] & b0[next_offset + j];`

逐字计算下一行 fire 并覆盖 f_next。这个容器可能刚从上一轮的 f_prev 换回来，所以每一字都要赋值，不能将新旧火用 |= 合并。

**拿数字验一下**：设出发时 f_prev 装第 4 行、f_curr 装第 5 行，算第 5 行前在这里读入第 6 行。算完交换后，第 6 行已经是 f_curr，算它时只需把第 7 行读进 f_next；这就是为什么循环每次只新解码一行。

**第 184 行** · `} else {`

else 只在真实底行执行，因为地图外没有下一行可以传播火。当前线程末行不一定是全图底行。

**第 185 行** · `std::fill(f_next.begin(), f_next.end(), 0);`

把 f_next 整行清成无火。若末行还沿用上一轮留下的位，底边会像接了一行看不见的着火森林。

**第 186 行** · `}`

合上‘取真下邻或补零’的分支。从这里起，三个窗口均就绪，内层计算不必对每个格子的上下方向判断越界。

**第 187 行**

空行区分装载邻行与写本行。只有前一个阶段使用 r+1 作为下邻，写回目标一直属于 r。

**第 188 行** · `size_t curr_offset = size_t(r) * W;`

算当前行的全图字偏移，稍后定位目标图与当前两面。它与 f_curr 不同：后者本来只是一行，按 j 取即可。

**把窗口贴成三张卡，再移动两次。** 假设 n=8，线程专管真行 3..5。开头 f_prev 来自第 2 行，f_curr 来自第 3 行。沿代码读出下面每一轮窗口的内容；表中数字是旧图的行号，不是火的数量。

|准备更新的行|prev|curr|新装入 next|刚写的是谁|
|---:|---:|---:|---:|---|
|3|2|3|4|新图第 3 行|
|4|3|4|5|新图第 4 行|
|5|4|5|6|新图第 5 行|

走到第 5 行时，这个线程手里已经有第 6 行的旧火，但它不应顺便写第 6 行。否则和其他线程的任务重叠。读权限的范围是负责行段再向上下各伸一行，写权限的范围却恰好等于行段。若全图只有一行，则 prev 和 next 同时补零；小例能检验边界分支，但不能替代跨线程分界的例子。

**为什么只需存火，不需存所有邻居的状态**：目标格只有两种询问。它自己是什么，用本格原来的 b1、b0 直接回答。它能否被点燃，需要的只是邻居是不是火，不关心它是树、灰还是空中的哪一种非火。把邻居压成一个真假并没有丢掉转移所需的信息。

**这段结束后的状态**：进入内层字循环前，三个数组分别对应 r−1、r、r+1 的火；全图边沿用全零代替缺少的行。

**写错会怎样**：把 r< n 误写成 r<end_r，会在人为分工接缝上造一条防火线。两条相邻线程都可能算出一行不易察觉的错格。

**和前后版本的关系**：v4–v6 用共享火平面的上下两行。v7 在每个线程里自己解码，不需要等待别人先写火图。

**一句话记住**：只在地图边沿补零，线程边沿照读邻行。

## 第 189–221 行 · 把四邻火投到树上，等全图写完

**这段在干什么**：看一字的 64 格。左、右运算不是让旧火改变位置，而是在目标格上标记‘这个方向有火’。上、下旧火行已经和目标行列号对齐，不需要移位。

**逐行讲解**

**第 189 行** · `for (int j = 0; j < W; ++j) {`

j 依次取当前行第 0 到 W−1 个字。若误用 j<n，这里会把格子个数当字个数，远远越过只装一行的窗口。

**第 190 行** · `uint64_t f = f_curr[j];`

把当前字的火复制到局部整数 f，后续两个方向都用这份旧火。它是 64 个真假值，不是‘本行共有多少火’这个计数。

**第 191 行** · `uint64_t L = (f << 1) | (j > 0 ? f_curr[j - 1] >> 63 : 0ULL);`

f<<1 使位 k 的火标到候选目标 k+1；上一字最高位右移 63 后落在本字位 0。两者按位或合并。j=0 时左边是地图外，不能去取 f_curr[−1]。

**拿数字验一下**：把位序画成左字 [63 … 0]、右字 [63 … 0]，注意书写时最高位在左、实际列号越大位越高。若左字只在位 63 有火，右字 f=0，(f<<1) 本身为零；补入那一位才让右字位 0 知道左方着火。

**第 192 行** · `uint64_t R = (f >> 1) | (j + 1 < W ? f_curr[j + 1] << 63 : 0ULL);`

镜像方向：f>>1 把旧火标到较小列；下一字的最低位左移 63，以它补本字最高位。例：列 64 有火能点第 63 列，而不会从行末绕到下一行。

**拿数字验一下**：反向检验：若 j 是一行的末字，j+1<W 为假，就算内存里紧跟着下一行的首字，也必须补 0。否则地图末列会被下一行首列点燃，这两个格子并不是水平邻居。

**第 193 行** · `uint64_t nbr = L | R | f_prev[j] | f_next[j];`

四张对齐到目标列的候选图按位或，有任一方向来火就标 1。没有把 f 本身直接加进来，也没有对角线；本格是否是树留给第 196 行。

**拿数字验一下**：以八位演算，当前火 00000100，左右投影分别为 00001000 和 00000010；上方火为 00100000、下方无火，则候选为 00101010。它只说这三个目标旁有火；拿旧树再交一次才决定真正新火。

**第 194 行**

空行分开‘周围有没有火’与‘这里能不能点燃’。邻火掩码里标上灰或空地是允许的，下一步会筛掉。

**第 195 行** · `size_t idx = curr_offset + j;`

把当前行起点与字编号 j 相加，同时定位两张旧面和两张新面。所有面采用相同布局，否则表达式写得再对也会把两处格子拼成一个状态。

**第 196 行** · `uint64_t tree = b1[idx] & ~b0[idx];`

`tree = b1 & ~b0` 只选 10；`~` 是逐位翻转而不是逻辑非 !。后者只产生一个布尔值，把整个字除最低位外的信息都丢掉。

**第 197 行** · `uint64_t burn = tree & nbr;`

tree & nbr 把能着火的旧树与至少有一邻火的目标相交，burn 只代表新点燃的格。旧火不能再算作新点燃，因为这一步它要变灰。

**第 198 行**

空行提醒读者目前全是局部推导，旧图没有被改。下面才分别写新一代的两个问题的答案。

**第 199 行** · `nb1[idx] = tree;`

新高面等于所有旧树：未燃的仍是树，刚燃的成为火，这两种新状态高位都是 1。旧火这一拍变灰，高位恰好应清零，故不能复制旧 b1。

**拿数字验一下**：拿一列验真值：空地 00 → 00；旧树 10、无邻火 → 10；旧树 10、有邻火 → 11；旧火 11 → 01；旧灰 01 → 01。五行中输出高位都是‘输入是不是树’。这就是能直接赋 tree 的推导，不用背简化公式。

**第 200 行** · `nb0[idx] = b0[idx] | burn;`

新低面等于旧低面或新点燃集合。旧灰仍灰、旧火变灰都保留低位 1，新火也需要低位 1。若只写 burn，旧灰会被意外抹成空地。

**第 201 行** · `}`

合上一个个字的循环。现在只保证当前行的新状态已经写完，不代表别的行或别的线程都已结束。

**第 202 行**

空行把本行写回与滚动窗口的轮换分开。此刻还不能交换全局两代图。

**第 203 行** · `std::swap(f_prev, f_curr);`

交换 f_prev、f_curr 两个容器的内容归属。以 A、B、C 分别记旧的上、中、下，执行后变成 B、A、C；不必按 W 个字复制一行。

**第 204 行** · `std::swap(f_curr, f_next);`

再交换中、下，得到 B、C、A：旧中成新上，旧下成新中，旧上的空间下轮重填。把两次交换顺序颠倒会让窗口反向轮换。

**第 205 行** · `}`

合上本线程逐行循环。所有自己负责的真行已经写到 next 面；暂时仍不能在别的线程面前发布新图。

**第 206 行** · `}`

合上非空行段的判断。连没有分到行的线程也会抵达下方等待，这才能使参与者人数与建队时一致。

**第 207 行**

空行结束并行计算正文。它没有同步作用；如果没有后面的指令，快线程可以继续跑。

**第 208 行**

纯注释提示显式等待的位置。它和第 166 行一样不生成指令，但这次下一行确实有一条单独的栅栏指令。

**第 209 行** · `#pragma omp barrier`

#pragma omp barrier 要求团队全部到达，并让等待前的结果在同步后可见。如果只有 single 而没有这道入口前的等待，快线程可能在慢线程写完前交换容器。

**拿数字验一下**：做个时序实验：甲负责行 1–4，刚写完就把 b1 与 nb1 换位；乙还在算行 7，要从旧 b1 读行 8。若乙这时读到的是新面，甚至可能把旧低面和新高面拼成并不存在的状态。两人不写同一行也会出错，原因在共用容器的角色发生了变化。

**第 210 行**

空行标志从各写各行过渡到一次性的全局交换。有了上一行的等待，这里才能把整张下一代当作完整结果。

**第 211 行**

注释里的‘交换指针’是直观简称；实际对 std::vector 使用 swap，不去修改某个格子的指针，也不逐字复制。

**第 212 行** · `#pragma omp single`

single 只选一人交换全图。若每个人都交换，偶数次可能又回到旧图，更糟的是并发修改同一容器没有正确同步。

**第 213 行** · `{`

开启交换和累计计时共用的单人块。只保护其中一个位面的交换会导致两面来自不同时间。

**第 214 行** · `std::swap(b1, nb1);`

把高面的新旧容器互换，原来的旧存储供下一轮覆盖。到这行两面暂时不同代，因此需要把下一行也留在同一个发布阶段。

**第 215 行** · `std::swap(b0, nb0);`

同样交换低面，完成完整一代的发布。不必清零旧面，因为下一步转移对每个真行的每一字都做完整赋值。

**第 216 行** · `ms_move += ms_since(t_step);`

在等齐和两次交换之后累计 move 耗时。它是包含等待和组织工作的经过时间；称‘精确’不表示测得纯内核运算时间或每个线程各自的工作量。

**拿数字验一下**：一个线程算得慢时，其他线程抵达 barrier 后停住，move 的读数仍在走。即使两份实现对每一字调用相同数量的位运算，只要任务分得不均、等待不同，记录的 move 就可能差很多。

**第 217 行** · `}`

合上第二个 single；默认末尾再次同步。若去掉等待，某些线程可能直接开始新一轮事件，读到尚未成对交换的状态。

**第 218 行**

注释指向上一行附带的隐式栅栏，并没有增加第四次显式等待。比较同步数时按指令语义数，不按注释里出现几次 barrier 数。

**第 219 行** · `}`

结束当前 ts 的主体。未到 t 则所有线程一起回到第 124 行；到 t 后离开时间循环，当前面就是最终森林。

**第 220 行** · `}`

并行区在这里结束并汇合，线程的私有窗口离开作用域。随后串行写文件，不应由队内每个人各写一遍。

**第 221 行**

空行分开并行区和输出段。任务说明所称 221 行到这里甚至还没开始写文件，所以继续读到真实末行。

**拿一个完整的八位字走完转移。** 设本行只有一字，左右没有借位；旧高面 01010110、旧低面 01001100，上行火 00100000、下行火全零。旧火是 01000100，旧树是 00010010。算到哪一步都先写到草稿中，不在半途中动旧面。

|---|---|---|
|左方向候选（旧火左移一位）|10001000|位 7、3 的左邻有火|
|右方向候选（旧火右移一位）|00100010|位 5、1 的右邻有火|
|四向并集|10101010|只说明邻火存在，不说明这里是树|
|新点燃＝旧树与四向并集|00000010|只有位 1 同时满足两条件|

|下一代 b0|01001110|旧低位保留，新火位 1 加入|

读回位 1 是 11，确实成了火；位 2 从 11 到 01，是灰；位 4 仍 10，是树。一个向量例里同时看到三种变化，比孤立背两条赋值语句更能检验自己是否真读懂。再把上行火改成 00010000，只应额外点燃位 4，而不能影响位 0；这是四邻与位对齐的快速复核。

**两个尺度的交换**：一行写完就轮换三个私有窗口，全步写完才轮换两张全局状态面。若你在第 205 行之后急着画一张“全图已新”的图，就会把这两个尺度弄混。

**这段结束后的状态**：这一时间步的两张新面都已成为当前图；线程通过交换后的同步点，才能进入下一次事件处理。

**写错会怎样**：旧火要变灰，新火要保留一拍。若 nb1 只写没被点燃的树，刚点燃格便会落入 01（灰）而不是 11（火）。

**和前后版本的关系**：v6 的四邻公式相同但火的取址不同。v8 把同步显式化，br 则连两位编码都不同。

**一句话记住**：先写全一代，再发布这一代。

## 第 222–261 行 · 把位平面翻译回人能读的森林

**这段在干什么**：模拟结束，重新按真行真列走一遍，把两个真假合成表下标，写出数字字符和分隔符。一行恰好 n 个字段，补齐字的高位永远不输出。

**代码块**：

**逐行讲解**

**第 222–224 行**

三行注释划出缓冲输出段。打印森林和打印计时使用不同目的地，结果文件不得混入时间标签。

**第 225 行** · `t0 = Clock::now();`

把可复用的起点 t0 设置到输出开始。总起点 t_all 仍保留，第 255 行读的是输出段，第 258 行读的是全过程。

**第 226 行**

空行把计时与打开文件隔开；因此打开和关闭文件的时间也属于输出阶段。

**第 227 行** · `FILE* fo = std::fopen(argv[2], "wb");`

fopen(argv[2],"wb") 以二进制写模式打开输出，已有文件通常会被截短，失败返回空指针。二进制模式仍能写文本，只是不做平台换行转换。

**第 228 行** · `if (!fo) { std::fprintf(stderr, "open out failed: %s\n", argv[2]); return 1; }`

检查输出文件指针；若打开失败，把真实路径写到 stderr，再返回失败，不会假装森林已生成。这只能发现打开时的问题，不能发现稍后的磁盘写满。

**第 229 行**

空行把文件准备和内存缓冲区准备分开。输出通道已经打开，但还没有格子写入。

**第 230 行** · `std::vector<char> obuf(1 << 22);`

1<<22 在目标平台上得到 4,194,304；`vector<char>` 以字节为单位分配 4 MiB。每格恰好写两字符，一块能装 2,097,152 格。

**拿数字验一下**：若缓冲用八字节来模拟，四格‘1 2 3 0\n’刚好用满；下一格到来前须刷新。刷新按当前长度写出并复位，不需要每写一格都去问操作系统。用这个小例同时检查‘恰满’与‘还有尾部’两种情况。

**第 231 行** · `char* q = obuf.data();`

q 是下一次写入的可写地址，开始指向缓冲区首部。这里不用 const，因为要经 *q 修改内容；变量 q 的移动不改变容器大小。

**第 232 行** · `char* qend = q + obuf.size();`

qend 是容器末尾之后的合法哨点，不能解引用。剩余容量应从 qend 与 q 的距离理解，不能把它当作末尾那个可写槽的地址。

**第 233 行**

空行分隔游标设置与刷新过程。刷新的是‘目前已经填的’部分，不等于每次把整块内存写出去。

**第 234 行** · `auto flush = [&]() {`

flush 是按引用捕获的小函数，不带参数。这样既能看到最新的 q，也能在调用后把同一个 q 复位；不是标准库里同名的流操纵符。

**第 235 行** · `std::fwrite(obuf.data(), 1, size_t(q - obuf.data()), fo);`

fwrite 写入从首地址开始的实际字节数 q−data()，每项 1 字节。指针相减要求属于同一数组；它返回写成的项数，这里未检查，所以磁盘错误未必能在退出码中反映。

**第 236 行** · `q = obuf.data();`

刷新后把游标放回开头，下一批覆盖旧内容即可。不必先 memset 清零：写出长度由新的 q 决定，旧尾部不会混入文件。

**第 237 行** · `};`

合上 lambda 定义并用分号结束赋值声明。到这里仅得到一个函数对象，还没有触发任何实际写入。

**第 238 行**

空行隔开‘如何把字符送到文件’和‘该产生哪个字符’两件事。

**第 239 行** · `const char tbl[4] = {'0', '3', '1', '2'};`

表下标由两位 b1b0 构成：0→字符 0，1→字符 3，2→字符 1，3→字符 2。别把字符常量写成整数 0、3、1、2，否则文件里会出现控制字节。

**拿数字验一下**：反向核对：从输入的 2 经第 66、67 行得到 b1b0=11，拼成下标 3，tbl[3] 是字符 '2'。输入 3 得 01，下标 1 取 '3'。读入和输出互为反向不代表转移也正确，但能独立验证编码层。

**第 240 行**

空行切换到逐格解码。此时森林在当前面，nb1/nb0 是上一轮留下的存储，不应拿来输出。

**第 241 行** · `for (int i = 1; i <= n; ++i) {`

按内部行号 1..n 访问，跳过上下哨兵行。若额外输出一圈，森林本身可能算对了，格式仍不符题面。

**第 242 行** · `size_t row_offset = size_t(i) * W;`

行首偏移按字数 W 计算。第 i 行第一个真实格子在这一字的位 0；不要照字节数组版再加一个左边框。

**第 243 行** · `for (int j = 0; j < n; ++j) {`

逐列只走 n 个真格，哪怕尾字尚有填充位置也不输出。遍历 W×64 列会在 n=65 时多写 63 项。

**第 244 行** · `if (q + 2 > qend) flush();`

意图是在写数字和分隔符前确保还有两格空间，不足就 flush。须辨清：当 q 已等于 qend 时，q+2 本身超出数组允许的指针运算范围；更可靠的判断按剩余长度比较，详见附录 D。

**第 245 行** · `size_t idx = row_offset + (size_t(j) >> 6);`

用列号除以 64 找字，行首偏移找到对应行。它和读入第 76 行是互逆定位，用错一个下标可能仍输出 n² 个看似合法的数字。

**第 246 行** · `uint64_t bit = 1ULL << (j & 63);`

取一个单置位掩码选择该字内的列。位 63 也要用宽无符号常量，不能先用窄类型移到高位再转换。

**第 247 行** · `int v1 = (b1[idx] & bit) ? 1 : 0;`

三元表达式把 b1 与掩码的结果归一化成 1 或 0。若保留原掩码的数值，比如 1<<40，就不能把它当数组下标的高位。

**第 248 行** · `int v0 = (b0[idx] & bit) ? 1 : 0;`

对低面做同样的归一化。两面必须用同一字同一位；若误用上一列，四状态都可能仍合法，单看输出范围抓不出错。

**第 249 行** · `*q++ = tbl[(v1 << 1) | v0];`

先用 (v1<<1)|v0 拼出 0..3，再查表。*q++ 表示写入当前 q 所指的位置，随后指针前进；不是让缓冲里的字符本身加 1。

**第 250 行** · `*q++ = (j == n - 1) ? '\n' : ' ';`

非行末写空格，行末写换行字符 '\n'；q 一样向前。每格固定产生两字节，这一约定让缓冲容量和文件长度都可推算。

**第 251 行** · `}`

结束一行的列循环。末格已写下换行，所以行循环本身不必再补一个空白行。

**第 252 行** · `}`

结束所有真行。q 仍可能指向缓冲区中段；循环结束不等于这些尾部字符已由文件接口接收。

**第 253 行** · `flush();`

显式调用 flush() 写尾块。用 6×6 小例只产生 72 字节，不会触发容量检查；若漏此行，整幅小图都可能不出现在文件里。

**第 254 行** · `std::fclose(fo);`

fclose 将 C 文件流关闭，结束文件层的缓冲工作。第 253 行处理的是程序自己的向量，两级缓冲不能相互替代；本行返回值也没有检查。

**第 255 行** · `double ms_out = ms_since(t0);`

ms_since(t0) 得到输出阶段毫秒数。含逐格解码和写文件，不能只用它估磁盘速度，也不能把它算进 move。

**拿数字验一下**：原始大图的可见文本数据每格两字节，按纯 LF、每格一数字一分隔，输出应为 536,870,912 字节。这是格式推算。若程序只写了缓冲的末段或多打了一圈哨兵，长度就能提示从输出段开始排查。

**第 256 行**

空行把结果写入与诊断输出分开。即使屏幕上显示计时，森林的数字仍然只应该在目标文件中。

**第 257 行** · `fprintf(stderr, "read=%.1f event=%.1f move=%.1f out=%.1f total=%.1f\n",`

fprintf 以标准错误流为目的地；五个 %.1f 表示浮点数保留一位小数。此行用逗号续到下一行，同一个函数调用还没结束。

**第 258 行** · `ms_read, ms_event, ms_move, ms_out, ms_since(t_all));`

按格式占位的顺序给出读、事件、转移、输出和总时长。末尾那个当场用总起点求值。初始化、框架等待等口径存在差别，四项不必严格相加等于总数。

**第 259 行**

空行隔开诊断与正常返回。它不会等待别的 MPI 进程；v7 根本没有 MPI 协调多进程输出。

**第 260 行** · `return 0;`

main 正常返回 0 表示程序走完成功路径。它没有调用判题器，也没验证写出返回量，所以 0 不能证明结果正确或性能达标。

**第 261 行** · `}`

合上 main 的最外层花括号，局部容器等对象离开作用域并释放各自资源。到这里才是此份 v7 的物理末行。

**用八字节输出缓冲手推。** 忽略真实容量 4 MiB，假设只有八个字符槽。要写两行、每行三个格子，第一行 0 3 1，第二行 2 0 3。每格先写数字后写分隔符，第一行后的游标在第 6 格；第二行首项和空格占完余下两格。第二行第 2 格要写入前，旧内容必须刷出。以下用“空”和“换”显示通常看不见的字节。

**五张最小读码卡。** 每张卡故意只刁难一个接口。先写下预测，再去指定行验证。不需要相信一份“看上去像森林”的大图就一定是对的。

1. **一格旧火，零事件，一步。** 输入头 `1 0 1`，图只有 2。上下都补零，左右也没有邻字；树掩码为 0，旧低位保留，于是输出 3。这张卡检验新火与旧火是否混为一谈。若仍输出 2，去看 L199–200，而不是先调线程数。
2. **两棵相邻树，惊雷击左，走一步。** 把这两格放在一个 2×2 图的第一行，另一行全空。魔法后第一行是 2 1，步后应为 3 2。若得到 2 1，你看到的是魔法快照；若仍 1 1，去查点坐标的一基行与零基列；若第二棵树已是灰，可能把同一拍连做了两次转移。
3. **第 63 列是火，第 64 列是树。** 在 65×65 的图中只设这两格，其余全空，二者处于同一行。旧火在字 0 的最高位，树在字 1 的最低位；一步应为灰、火。将两个状态对调再走一遍，期望反向传回。两张互为镜像的卡分别检查 L191 和 L192，只有一个方向失败就不必从文件头重查。
4. **线程接缝上的火。** 令 n=4、两线程。内部真行 1、2 归甲，3、4 归乙；把火放在行 2 列 0，把树放在行 3 列 0。两行在不同团队成员的窗口中，却仍在同一张旧图上。若只在双线程出错、单线程正确，先找 L170–174 与 L181–185 是否把行段边缘当物理边缘。这里说的是排查方向，不是一项已做的计时实验。
5. **一个字全部回春，但没有任何火。** 令 n=64，某一行 64 格全灰，其他地方全空；回春矩形恰好等于那一行的 0..63 列。一轮结束该行应全为树，没有一格变火。它同时区分“整字掩码错误”和“灰被解成旧火”两种故障：若整行不动，先看 L151；若复活后仍自燃，查旧火的判定是否真是两个位相与。

**如何定位而不是盲改。** 对一个错误格，先写出期望输出的字符，再反查 tbl 得期望两位；核对两张新面里这个位，若对，问题就在导出；若不对，查看魔法后旧树位和四向邻火位。旧树位错回头查读入或魔法，邻火位错再分别查字接缝、行接缝和地图边缘。一次缩小一个区间，通常比盯着 261 行找“看起来很奇怪的符号”更有效。
