# 第 4 章　v8：评测没有打开 OpenMP，怎么办

**这一章你会得到什么**：看清作者换的是线程组织方式，而不是火势公式；能在纸上走完三个同步点，并指出哪些时间不能跨版本直接比。 代码框保留关键原行，行号不连续时，中间行见标注的源文件区间。

## 4.1　评测命令缺了什么

题面第 247–258 行给的是 `mpiicpx forest.cpp -O3 -xHost -o forest`，运行时另用 `mpirun ... -np 64`。编译驱动（compiler driver，组织编译和链接的工具）名字里有 MPI，保证不了同一进程内的循环被多线程分担。-O3 要求较高等级的优化，-xHost 允许为编译主机的指令集优化，-o 只指定输出文件名。三者都不等于 OpenMP 的启用选项。
    
v8 文件开头把没有 -fopenmp 列为迁移动机。按 [Intel 编译器文档](https://www.intel.com/content/www/us/en/docs/dpcpp-cpp-compiler/developer-guide-reference/2025-1/fopenmp.html)，默认不为这些指令生成多线程代码；Intel 也有 -fiopenmp 等启用方式，题面没有给出。若包装器没有额外代加，v7 的 pragma 不能组织一队线程；此时还要分两种情况：能链接到运行库，串行环境里团队为一人；无法解析 omp_get_num_threads 等符号，可能在链接阶段就失败。是否打印“忽略指令”的警告取决于工具配置，包里没有评测编译日志。v8 要消掉的正是这层依赖，不是 OpenMP 算不出正确答案。

## 4.2　三个人怎样在一道门后同时看到新数据

类（class，封装数据和方法的类型）里 public 是能从外部调用的部分，private 是内部状态。explicit 是显式构造约束，禁止拿整数自动冒充这个类的对象。看到 `std::atomic<unsigned>` 时先读作‘可以原子操作的无符号世代号’，不要把所有访问普通变量的动作也误认为原子。

原子变量（atomic variable，使多线程对该对象的特定读写不可分割的变量）解决的是‘几个人同时到站，别漏数’。仅有计数还不够，每一步要重复过同一道门，所以用世代号（generation，标识这是第几次会合的编号）。SpinBarrier 的构造器记住固定人数 n_，cnt_ 和 gen_ 从 0 开始；wait() 没有返回数据，返回本身表示这轮到齐。

设三人 A、B、C 看见 gen=5。A 的 fetch_add 返回旧数 0，B 返回 1，两人继续等；C 返回 2，加一恰为 3。C 把 cnt_ 归零，再把 gen 发布为 6；A、B 观察到改变便能离开。若只等 cnt_==0，跑得快的人下一轮已经把它加到了 1，慢人可能错过那瞬间。给每一轮单独的代号就不必赌是否恰好看到零。

获取与释放（acquire/release，建立线程间先后与可见性的原子内存顺序）在这里有明确方向。到站的读改写采用 acq_rel，接过先前到站者的工作并发布自己的工作；末位到站者把新世代以 release 写出；等待者用 acquire 读到新值之后，才能按前一阶段已经完成来用共享数据。计数清零用 relaxed，不单独传递其他数据，由后面的世代发布承接。_mm_pause 给某些处理器忙等提示，不是睡眠、互斥或同步的替代品。注释说比条件变量快一个量级，没有原始重复测量，不拿来填成绩表。

## 4.3　谁来工作，行少于人又怎么办

标准线程（std::thread，执行可调用对象的一条 C++ 线程）显式创建后会运行 worker(tid)。T 默认 16；getenv 查询环境变量 FIRE_THREADS，不存在返回空指针，存在则返回字符串地址；atoi 把字符串前部按整数解析，代码随后作下限和硬件提示的上限处理。hardware_concurrency 返回的是并行能力提示，允许为 0，不保证等于这个进程获调度的核数。特别是题面给了 I_MPI_PIN_DOMAIN=core，具体绑核结果必须看机器，不能承诺 16 个线程一定各占一核。

n=5、T=4 时 chunk=2，三人做行 1–2、3–4、5，第四人拿不到行。空闲线程把区间标成 0..−1，看似没有贡献却不能直接退出；人数已写进栅栏，如果只剩三个人再也过不了门。主线程编号为 0，pool 里只放 T−1 个新线程，不是再建 T 个然后让主线程闲等。join（thread join，等待指定线程结束）在模拟之外执行一次。v7 的并行区其实已经包住全部步数，不能说‘从 v7 到 v8 才发明常驻’。

## 4.4　把回春分出去，为什么惊雷仍归一个人

v7 的 single 内不论矩形多大都由一个人做。v8 让每人看相同的事件表和同样的步号，却给每人自己的 cnt_event。若共享一个游标并任一人先加，别人可能还没处理自己那几行，就把事件跳过了。惊雷只有一个目标，指定 tid==0 修改；回春则用 max(事件起点,区段起点) 与 min(事件终点,区段终点) 取行的交集，按列的首尾掩码仍沿用 v7 的做法。

试用三人分十行的例子：矩形内部行 3..7，线程 0 改 3..4、线程 1 改 5..7、线程 2 不改。两个线程不会对同一个 64 位字进行各自的读改写，因为它们写的是不同行。不应随意改成按格子均分；相邻两格可能在同一个字内，对不同位的普通 |= 也可能互相覆盖。题目保证同一步最多一个事件，所以在本实现中不必处理同一步多种魔法之间的先后依赖。

## 4.6　可选 MPI 是输出保护，不是四节点加速

条件编译（conditional compilation，编译前按条件保留或移除一段源码）由 __has_include 判断是否能找到 mpi.h。找到则定义 FIRE_HAS_MPI，从而在 main 中调用 MPI_Init 初始化、MPI_Comm_rank 查询自己在全局通信器 MPI_COMM_WORLD 中的编号，非零号调用 MPI_Finalize 收尾，不进入读图、算图与写图路径。收尾是集体操作，不能把注释‘立即退出’理解为必定立即结束整个系统进程。能找到头文件也不自动保证链接器找得到 MPI 库。

若用题面 64 个进程，启用了上述分支时 rank 0 持有整图，rank 1–63 都不分到任何格子；没有向其他节点传递行。若编译时完全没启用 MPI 分支，却用外部启动器起 64 份相同程序，分支不会凭空出现，各份进程仍可能抢写同一个文件。程序正常尾部配对 Finalize，但若 rank 0 在若干文件错误分支提前返回，其他进程退出的行为仍需留意。

## 4.7　并排看两版的边界

|问题|v7|v8|
|---|---|---|
|谁建团队|OpenMP parallel|标准库建 T−1 人，主线程加入|
|团队寿命|跨全部时间步|同样跨全部时间步|
|谁做事件|任选一人执行 single|惊雷给 0 号；矩形按行分|
|谁等谁|两个 single 末端与一道显式栅栏|每步显式三次 wait|
|位面、窗口、旧火规则|两面两代，各人三行火|数学不变|
|多进程输出|无 rank 保护|有 MPI 时仅 0 号；无 MPI 时无保护|
|move 的终点|等齐并交换后|0 号在第二道等待前取样|


**一句话记住**：一次迁移要对齐算法、同步和测量这三件事。
