CHAPTER 00

第 0 章　同一场火，两种时间

这一章你会得到什么：拿一支笔，在六行数字里找出下一步所有的火。能解释为什么新点燃的树不能立刻再烧一格，你就已经抓住了后面八个程序都不能改的规则。

0.1　从一棵树开始

这是一场格子游戏。时间步（time step，模拟的一轮）有两个时刻要分清：魔法刚执行完，和火势刚更新完。格子上的数字是状态（state，某一刻格子的取值），只有四种：0 是空地，1 是活树，2 是火，3 是灰。惊雷点一棵树，别的状态不动；回春把一个闭矩形里的灰变成树，别的状态不动。闭矩形就是上下左右端点都算在内，两端恰好相等也能选中一个格子。

魔法完成后，给森林拍一张“照片”。逐格看照片：树旁边的上、下、左、右只要有火，就在新纸上写 2；旧火一律写 3；其余原样抄。斜着挨到火没有用，地图左端也不和右端相接。惊雷点出的火已经在照片里，所以它这一拍就变成灰，也能点着邻树。刚被邻居传染的火却只出现在新纸上，它要等下一拍。源码里两张轮换的图就是这两张纸，叫双缓冲（double buffering，分别存放当前和下一状态）。

一句话记住：一轮可以先回春再着火，但火不能在同一次转移里连跳两格。

0.3　文件长什么样，什么叫相同

forest.in 和 forest.out 是文本文件（text file，以字符记录数据的文件）；字符 '2' 和内存中数值 2 不能直接互换。输入的事件按步号递增，同一步最多一个。回春行在类型 2 后另有四个整数：起始行、起始列、结束行、结束列。输出不再写尺寸和事件，只写最终的 n 行地图。程序诊断可以写到标准错误流（standard error，单独的诊断通道），不能混进森林数字。

context/gencase.py 第 20–37、71–85 行规定了生成器：初始按权重 15:83:2 随机产生空、树、火，没有初始灰；这不是说每个 100 格的小图必有 2 棵着火。总步数为 7 时，取整后回春 3 次、惊雷 2 次，其余两步无事。矩形两边长度分别随机取样并限制范围，所以成本要看实际矩形，不能把“有一个事件”当作恒定的一次写入。

实际比对工具 context/compare.py 第 7–29 行同时读两行，去掉首尾空白，再按连续空白分出字段（token，分隔后的一段文字）。每行字段数和对应字段字符串都要相等；比如 1 2 与 1 2 可以相同，01 2 与 1 2 不相同。它并没有逐字节比较，也没有验证每个字段一定是 0–3。逐行并行读取两个文件的写法还有一处尾行漏检可能，见附录 D。写程序仍按题目的 n 行、每行 n 项，不依赖脚本的宽容。

一句话记住：数值、写出来的字符和比对脚本眼里的字段，是三层不同的东西。

0.4　68 秒怎样变成 8.1 纳秒

题面给 4 个节点（node，一台独立机器），每节点 16 个核（core，可执行指令的处理单元），启动 64 个进程（process，拥有独立地址空间的程序实例）。同一个进程里的线程（thread，可共享内存的一条执行路径）不是另一台机器。消息传递接口（Message Passing Interface，进程间显式交换数据的接口，简称 MPI）让不同进程交换边沿；共享内存并行接口（Open Multi-Processing，共享内存多线程编程接口，简称 OpenMP）让同一进程把循环分给线程。

满图 16,384 × 16,384 = 268,435,456 格，2,000 步，共 536,870,912,000 次逻辑格更新。这是拿不同程序作比较的共同分母，不等于每个程序都访问了这么多次内存。68 秒须合计完成每秒约 78.95 亿格。墙钟（wall-clock time，从开始到结束的实际经过时间）除以全部更新是 0.127 纳秒/格；如果理想地让 64 核平均分工，每核可花的时间才是 68 × 64 × 10⁹ / 536,870,912,000 = 8.11 纳秒/格。不要把两个数字都叫“每格耗时”然后直接相减。若实际上只用一个节点的 16 核，同一 68 秒只给每核约 2.03 纳秒/格；读写文件和等待还会占掉其中一部分。

正确且 110 秒时 40 分，正确且 68 秒时 150 分。在线性区内，每省一秒约增 (150−40)/(110−68) = 2.62 分；89 秒恰在中点，对应 95 分。以上都是从题面推算，没有跑比赛，也没有把 89 秒记到任何一个版本名下。

一句话记住：8.1 是把 64 核全部用起来才有的预算，不是运行记录。

位（bit，一个只能为 0 或 1 的位置）可以组成一个 64 位字（word，这里是装 64 个位的无符号整数）。位平面（bit-plane，把很多格子的同一属性并排存成一张位图）让一条逐位逻辑运算同时作用于 64 格。行窗口（rolling window，只保留眼下需要的相邻几行）和分块（tile，可独立调度的小片地图）都利用相邻关系，但解决的不是同一个问题。

1.1　v1　让每个判断都能用手指着读

读这个版本会用到三种基础写法。int（integer，整数类型）存格子状态；if（conditional statement，条件判断）表示条件成立才执行；for（for loop，计数循环）控制行列。std::cin（standard input stream，标准输入流）的 >> 从字符里解析一个整数；std::cout（standard output stream，标准输出流）的 << 向外写。这里的双尖号不是位移。方括号 [i] 以从零起的下标访问容器，访问者自己负责范围。

这一版想干什么：先把第 0 章那两张纸写成程序。二维数组（two-dimensional array，用行列两个下标取格子）读起来像方格纸。这里实际用嵌套向量（nested vector，外层容器保存一排内层容器）：sta[r][c] 要先找到第 r 行，再找到那一行的第 c 格。地图四周多一圈初值为零的格子，靠边的树也能照常检查四个方向。

卡在哪：题目规模上有约 2.68 亿格。按常见四字节整数（int，通常用来存放普通整数）估算，一张实心地图已经约 1 GiB；额外两圈和每行容器还没计入。一轮要把旧图完整复制给临时图，算完又把临时图赋回去。即便这一步一棵树都没烧，这两处依然要触碰整片内存。

1.2　v2　把复制改成交换，把字符攒成块

先分清地址和内容。指针（pointer，保存地址的值）写成 char* p；*p 取该地址的一个字符，++p 改的是地址。只读限定 const（const qualifier，通过这个名字不可改所指值）不妨碍 p 移动。fopen、fread、fclose 分别负责开流、读若干项、关流；一次读取返回的‘项数’只有在每项一字节时才等于字节数。while（while loop，条件成立就反复执行）适合数量未知的连续空白。

1.3　v3　让一个格子占一个字节

uint8_t（unsigned eight-bit integer，八位无符号整数）表示 0–255；std::size_t（size type，对象大小类型）适合装内存中的元素数或下标。static_cast<T>(x)（explicit type conversion，显式类型转换）要求将 x 转换成 T，并不能代替对 x 是否在允许范围内的检查。

这一版想干什么：字节（byte，通常由八个位组成）装得下 0 到 3。把很多独立的行改成一条长带子，行跨度（stride，从本行同一列走到下一行同一列要跨多少元素）直接参加下标计算。这样相邻行也位于同一片连续分配的空间里。

卡在哪：把第 r 行误算为 r×n 会跳错地方：作者沿用了上下左右各一格的空边框，真正行宽是 n+2。以 n=6 为例，第二行第二个内部格子用内部坐标 (2,2) 算得 18；把步长写成 6 就变成 14，仍可能落在合法内存中，所以只看程序有没有崩是不够的。

这一版改了什么：第 35–41 行检查实际读入字节；第 60–63 行让 stride 成为适合表示内存大小的无符号类型，并用两个连续的 uint8_t 容器存两代。第 134–149 行的上下邻分别在 idx−stride 和 idx+stride，左右只差 1。static_cast 是显式类型转换，让编译器检查这类转换是否合法；它并不会自动检查所有乘法是否超界。

1.4　v4　并排放同一件事的答案

三个运算先在一位上试：按位与（bitwise AND，逐位取交集）在两边皆为 1 时得 1；按位或（bitwise OR，逐位取并集）在任一边为 1 时得 1；按位取反（bitwise complement，把每位 0 和 1 对调）写作 ~。左移、右移（bit shifts，把无符号数中的位向高位或低位搬）这里才用 <<、>>。uint64_t（unsigned 64-bit integer，六十四位无符号整数）把这套演算放大到一排 64 格。

这一版想干什么：位运算（bitwise operation，对一个字中每一个二进制位置独立做逻辑运算）在这里有一个直观用途：一行 64 格的问题“哪些格是火”只要一对字就能回答。作者不给每格写两位相邻的编码，而是把同一种属性的 64 个位放在同一字中。

拿数字验一下：位置图可画成‘开头 0 → 中间 1、2、3 → 末端 4’。四字节文件末端的位置是 4，不是末尾那个字节的编号 3。正因为这个差一，后面可以直接申请 fsz 个有效字符，而不用再给实际长度加一。

第 33 行 · long fsz = std::ftell(fp);

ftell(fp) 查询当前文件位置并以 long 返回。此刻在末端，普通可定位二进制文件的位置才可用作字节长度。失败能返回负值，源码没有在分配前拦截。

第 34 行 · std::fseek(fp, 0, SEEK_SET);

用 SEEK_SET 作基准、偏移 0，把位置移回开头；不回去会从末尾开始读，读不到刚量出的那些字节。

第 35 行

第 36 行 · std::vector<char> buf(fsz + 1);

vector<char> 按 fsz+1 个字符分配连续空间。多出的一个位置用于第 44 行的零字符；不是说文件里还应该多读一个字节。

第 37 行 · size_t got = std::fread(buf.data(), 1, fsz, fp);

拿数字验一下：试读 5 项，结果返回 3，就只允许把前 3 项称为文件提供的数据。这也是为什么此处先比较 got，再向 buf[fsz] 写哨兵；写了哨兵不能让缺失的两个文件字节重新出现。

第 38 行 · if (got != size_t(fsz)) {

把长度转成 size_t 再与实读量比较，意在发现短读。函数式转换 size_t(fsz) 不检查负数；测长本身仍有前提，不能拿类型统一当作输入检查。

格式串的 %ld 匹配 long，%zu 匹配 size_t。把预期和实收的两个数都打印，能区分‘文件打不开’和‘打开后没读齐’。

第 40 行 · std::fclose(fp);

短读路径在退出前 fclose(fp)，释放这个文件流。不能指望后面的正常关闭替它办事，因为下一行已经返回。

第 41 行 · return 1;

此处返回失败，不拿部分文本当完整森林。少读的部分即便暂时碰巧是零，也不是用户提供的地图。

第 42 行 · }

第 43 行 · std::fclose(fp);

成功时关闭磁盘文件，之后扫描的是内存里的副本。关闭文件不会使 buf.data() 失效，因为容器拥有那段内存。

第 45 行

第 46 行 · const char* p = buf.data();

拿数字验一下：若文本是 6 空格 1，内存有四个位置：0 是 '6'、1 是空格、2 是 '1'、3 是哨兵。数字 1 的地址小于 end，读完它正好等于 end。此时再读一次，返回零同时不前进，所以非法的缺字段需要调用者另行发现。

每调用一次就从 v=0 开始构造新整数。不能把上一个数字的结果留在 v 里，否则输入 12 空格 3 可能拼成 123。

第 53 行 · return v;

第 54 行 · };

第 56–58 行

第 60 行 · int W = (n + 63) >> 6;

第 62 行

第 63 行 · std::vector<uint64_t> b1(total_words, 0), b0(total_words, 0);

拿数字验一下：拿八个输入格 0 1 2 3 1 0 2 0 缩小演算。把第 0 列写在纸最右端，b1 是 01010110，b0 是 01001100。把这两串与起来得到 01000100，只有位 2 和 6 是火，和输入中两个 2 对上。

第 64 行 · std::vector<uint64_t> nb1(total_words, 0), nb0(total_words, 0);

第 65 行

空行隔开储存空间和编码规则。名字 nb1 中的 n 指下一代，不是地图边长。

第 66 行 · const uint64_t b1bit[4] = {0, 1, 1, 0};

拿数字验一下：一张查表写在纸上：输入值 → 高面回答：0→否、1→是、2→是、3→否。‘高面’只是我在这张卡上给 b1 的位置，不能推出题面数字 1 的高二进制位也是 1。要先约定编码，再对外输出。

第 67 行 · const uint64_t b0bit[4] = {0, 0, 1, 1};

第 111 行 · #pragma omp parallel

第 112 行 · {

左花括号给并行指令划定作用范围。每个参与者都进入同样的代码，下一行读到的线程数相同，编号则各不相同。

第 113 行 · int num_threads = omp_get_num_threads();

omp_get_num_threads() 无参数，返回当前团队真实线程数，不是整机核数。算行段要用实际参与者：按设想的 16 人分，实际 4 人到场就会有行没做。

第 114 行 · int tid = omp_get_thread_num();

omp_get_thread_num() 返回团队内从 0 开始的编号。它用于分配行段，不是操作系统进程号，也不等于这次 single 的执行者。

第 116 行 · int chunk = (n + num_threads - 1) / num_threads;

起点 tid×chunk+1 把分段编号转成内部一基行号。tid=0 从 1 起，tid=1 从 5 起；省略 +1 会把第 0 行哨兵当真行。

第 123 行

第 125 行

第 126 行

第 201 行 · }

第 202 行

第 203 行 · std::swap(f_prev, f_curr);

第 204 行 · std::swap(f_curr, f_next);

第 208 行

第 211 行

第 212 行 · #pragma omp single

第 213 行 · {

第 214 行 · std::swap(b1, nb1);

第 215 行 · std::swap(b0, nb0);

第 216 行 · ms_move += ms_since(t_step);

第 217 行 · }

第 218 行

第 219 行 · }

第 220 行 · }

并行区在这里结束并汇合，线程的私有窗口离开作用域。随后串行写文件，不应由队内每个人各写一遍。

第 221 行

逐行讲解

第 222–224 行

三行注释划出缓冲输出段。打印森林和打印计时使用不同目的地，结果文件不得混入时间标签。

第 225 行 · t0 = Clock::now();

把可复用的起点 t0 设置到输出开始。总起点 t_all 仍保留，第 255 行读的是输出段，第 258 行读的是全过程。

第 226 行

空行把计时与打开文件隔开；因此打开和关闭文件的时间也属于输出阶段。

第 227 行 · FILE* fo = std::fopen(argv[2], "wb");

fopen(argv[2],"wb") 以二进制写模式打开输出，已有文件通常会被截短，失败返回空指针。二进制模式仍能写文本，只是不做平台换行转换。

第 228 行 · if (!fo) { std::fprintf(stderr, "open out failed: %s\n", argv[2]); return 1; }

检查输出文件指针；若打开失败，把真实路径写到 stderr，再返回失败，不会假装森林已生成。这只能发现打开时的问题，不能发现稍后的磁盘写满。

第 229 行

空行把文件准备和内存缓冲区准备分开。输出通道已经打开，但还没有格子写入。

第 230 行 · std::vector<char> obuf(1 << 22);

1<<22 在目标平台上得到 4,194,304；vector<char> 以字节为单位分配 4 MiB。每格恰好写两字符，一块能装 2,097,152 格。

拿数字验一下：若缓冲用八字节来模拟，四格‘1 2 3 0\n’刚好用满；下一格到来前须刷新。刷新按当前长度写出并复位，不需要每写一格都去问操作系统。用这个小例同时检查‘恰满’与‘还有尾部’两种情况。

第 231 行 · char* q = obuf.data();

q 是下一次写入的可写地址，开始指向缓冲区首部。这里不用 const，因为要经 *q 修改内容；变量 q 的移动不改变容器大小。

第 232 行 · char* qend = q + obuf.size();

qend 是容器末尾之后的合法哨点，不能解引用。剩余容量应从 qend 与 q 的距离理解，不能把它当作末尾那个可写槽的地址。

第 233 行

空行分隔游标设置与刷新过程。刷新的是‘目前已经填的’部分，不等于每次把整块内存写出去。

第 234 行 · auto flush = [&]() {

flush 是按引用捕获的小函数，不带参数。这样既能看到最新的 q，也能在调用后把同一个 q 复位；不是标准库里同名的流操纵符。

第 235 行 · std::fwrite(obuf.data(), 1, size_t(q - obuf.data()), fo);

fwrite 写入从首地址开始的实际字节数 q−data()，每项 1 字节。指针相减要求属于同一数组；它返回写成的项数，这里未检查，所以磁盘错误未必能在退出码中反映。

第 236 行 · q = obuf.data();

刷新后把游标放回开头，下一批覆盖旧内容即可。不必先 memset 清零：写出长度由新的 q 决定，旧尾部不会混入文件。

第 237 行 · };

合上 lambda 定义并用分号结束赋值声明。到这里仅得到一个函数对象，还没有触发任何实际写入。

第 238 行

空行隔开‘如何把字符送到文件’和‘该产生哪个字符’两件事。

第 239 行 · const char tbl[4] = {'0', '3', '1', '2'};

表下标由两位 b1b0 构成：0→字符 0，1→字符 3，2→字符 1，3→字符 2。别把字符常量写成整数 0、3、1、2，否则文件里会出现控制字节。

拿数字验一下：反向核对：从输入的 2 经第 66、67 行得到 b1b0=11，拼成下标 3，tbl[3] 是字符 '2'。输入 3 得 01，下标 1 取 '3'。读入和输出互为反向不代表转移也正确，但能独立验证编码层。

第 240 行

空行切换到逐格解码。此时森林在当前面，nb1/nb0 是上一轮留下的存储，不应拿来输出。

第 241 行 · for (int i = 1; i <= n; ++i) {

按内部行号 1..n 访问，跳过上下哨兵行。若额外输出一圈，森林本身可能算对了，格式仍不符题面。

第 242 行 · size_t row_offset = size_t(i) * W;

行首偏移按字数 W 计算。第 i 行第一个真实格子在这一字的位 0；不要照字节数组版再加一个左边框。

第 243 行 · for (int j = 0; j < n; ++j) {

逐列只走 n 个真格，哪怕尾字尚有填充位置也不输出。遍历 W×64 列会在 n=65 时多写 63 项。

第 244 行 · if (q + 2 > qend) flush();

意图是在写数字和分隔符前确保还有两格空间，不足就 flush。须辨清：当 q 已等于 qend 时，q+2 本身超出数组允许的指针运算范围；更可靠的判断按剩余长度比较，详见附录 D。

第 245 行 · size_t idx = row_offset + (size_t(j) >> 6);

用列号除以 64 找字，行首偏移找到对应行。它和读入第 76 行是互逆定位，用错一个下标可能仍输出 n² 个看似合法的数字。

第 246 行 · uint64_t bit = 1ULL << (j & 63);

取一个单置位掩码选择该字内的列。位 63 也要用宽无符号常量，不能先用窄类型移到高位再转换。

第 247 行 · int v1 = (b1[idx] & bit) ? 1 : 0;

三元表达式把 b1 与掩码的结果归一化成 1 或 0。若保留原掩码的数值，比如 1<<40，就不能把它当数组下标的高位。

第 248 行 · int v0 = (b0[idx] & bit) ? 1 : 0;

对低面做同样的归一化。两面必须用同一字同一位；若误用上一列，四状态都可能仍合法，单看输出范围抓不出错。

第 249 行 · *q++ = tbl[(v1 << 1) | v0];

先用 (v1<<1)|v0 拼出 0..3，再查表。*q++ 表示写入当前 q 所指的位置，随后指针前进；不是让缓冲里的字符本身加 1。

第 250 行 · *q++ = (j == n - 1) ? '\n' : ' ';

非行末写空格，行末写换行字符 '\n'；q 一样向前。每格固定产生两字节，这一约定让缓冲容量和文件长度都可推算。

第 251 行 · }

结束一行的列循环。末格已写下换行，所以行循环本身不必再补一个空白行。

第 252 行 · }

结束所有真行。q 仍可能指向缓冲区中段；循环结束不等于这些尾部字符已由文件接口接收。

第 253 行 · flush();

显式调用 flush() 写尾块。用 6×6 小例只产生 72 字节，不会触发容量检查；若漏此行，整幅小图都可能不出现在文件里。

第 254 行 · std::fclose(fo);

fclose 将 C 文件流关闭，结束文件层的缓冲工作。第 253 行处理的是程序自己的向量，两级缓冲不能相互替代；本行返回值也没有检查。

第 255 行 · double ms_out = ms_since(t0);

ms_since(t0) 得到输出阶段毫秒数。含逐格解码和写文件，不能只用它估磁盘速度，也不能把它算进 move。

拿数字验一下：原始大图的可见文本数据每格两字节，按纯 LF、每格一数字一分隔，输出应为 536,870,912 字节。这是格式推算。若程序只写了缓冲的末段或多打了一圈哨兵，长度就能提示从输出段开始排查。

第 256 行

空行把结果写入与诊断输出分开。即使屏幕上显示计时，森林的数字仍然只应该在目标文件中。

第 257 行 · fprintf(stderr, "read=%.1f event=%.1f move=%.1f out=%.1f total=%.1f\n",

fprintf 以标准错误流为目的地；五个 %.1f 表示浮点数保留一位小数。此行用逗号续到下一行，同一个函数调用还没结束。

第 258 行 · ms_read, ms_event, ms_move, ms_out, ms_since(t_all));

按格式占位的顺序给出读、事件、转移、输出和总时长。末尾那个当场用总起点求值。初始化、框架等待等口径存在差别，四项不必严格相加等于总数。

第 259 行

空行隔开诊断与正常返回。它不会等待别的 MPI 进程；v7 根本没有 MPI 协调多进程输出。

第 260 行 · return 0;

main 正常返回 0 表示程序走完成功路径。它没有调用判题器，也没验证写出返回量，所以 0 不能证明结果正确或性能达标。

第 261 行 · }

合上 main 的最外层花括号，局部容器等对象离开作用域并释放各自资源。到这里才是此份 v7 的物理末行。

4.2　三个人怎样在一道门后同时看到新数据

类（class，封装数据和方法的类型）里 public 是能从外部调用的部分，private 是内部状态。explicit 是显式构造约束，禁止拿整数自动冒充这个类的对象。看到 std::atomic<unsigned> 时先读作‘可以原子操作的无符号世代号’，不要把所有访问普通变量的动作也误认为原子。

看随包 spin_lock.hpp。flag 是原子布尔，false 表示无人占锁。lock() 用 exchange(true,acquire) 写入 true 并返回旧值；读到 false 的那个人拿到锁，读到 true 的继续循环。unlock() 用 release 写回 false，下一位成功获取锁的人能在正确顺序下看到上位留下的队列状态。lock_guard 是作用域锁卫士：构造时上锁，离开花括号、遇到 return 时也会析构解锁。所谓‘不用 mutex’是没有拿 std::mutex 当那把队列锁；源码仍引用 mutex 头里的通用 lock_guard。

自旋（spin waiting，反复检查直到条件满足）可能适合非常短的任务领取，但并不保证公平，也不保证一定比休眠划算。若持锁线程没获调度，其他线程会不断消耗处理器时间。代码没有用条件变量，没有等待新任务出现的休眠消费者；A 空就结束这一轮取任务，B 里的任务要等下一步。

5.10　常驻池：SpinBarrier、process_tasks 和 worker

5.12　手推一对相邻块：何时可以不算

画两个横向相邻块 U、V。第 k 步后只有 U 的最右列出现新火，V 最左列是一棵树。U 的 right_burn 被设为非零，所以 U 与 V 都在 k+1 的 A 中。处理 V 时，curr[-1] 读 U 边字，_shld<1> 把那一位引到 V 第一位，于是 V 的树成为新火。U 的旧火这拍要变灰，因此 U 也绝不能因‘火已经向右传’而跳过。等大家写完 next，才交换 U、V 的链接，其他未动的块继续保留 current。这串因果能同时检验字边界、块边界、活动队列和双缓冲。

把两个块改成分属不同进程，故事在何处断开？V 不能直接解引用另一个进程的地址。它要收到 U 的火边，解包进自己的 halo，补上 V 的入队请求，再执行同一内核。br 源中局部算子与打包器都能指出来，但实际入口没有组装这条跨进程路径。两位作者都用位平面与线程；v1→v8 并非一直使用同一布局，v8 相对 v7 才是基本保留布局而换团队；br 相对这两版既换编码又换了调度单位。这个区分能防止把‘少算一些块’误归功给另一种线程库。

附录 B　复杂度与性能账本

这一章你会得到什么：给定边长、步数和实际参加工作的核数，能算出容量、逻辑工作量和时间预算，也知道哪里必须停下来要实测数据。

B.1　先讲记账单位

设 n 为边长，t 为步数，W=⌈n/64⌉，P 为单进程实际工作线程数；Z=(n+2)W 是作者位图中一张面的字数。下表统计主要状态空间，输入文本、事件记录、输出缓冲另记。时间复杂度（time complexity，规模增大时操作次数的增长方式）和空间复杂度（space complexity，活跃存储随规模增长的方式）不是秒数或内存监控截图。按字计的一轮 nW 与按格计的 n² 在固定位宽机器上的渐近阶仍相同，差的是每次操作干多少格。

B.2　一张纸算完内存

二进制容量单位：1 KiB=1024 字节，1 MiB=1024 KiB，1 GiB=1024 MiB。取 n=16384，则 W=256，Z=4,194,816 字。一张带上下填充的位面用 33,558,528 字节，即 32 MiB 加 4 KiB。四张面约 128 MiB，第五张再加约 32 MiB。若 P=16，三行窗口合计 3×8×256×16=98,304 字节，即 96 KiB。两者之差是容量数量级，不代表每步都从主存传了同样多；芯片缓存能复用一部分数据。

按 LF、一位数字与一个分隔符计，大图格子文本约 512 MiB，还没算头行和事件。v2–v7 一次读完整文件，不能只看 v7 的 128 MiB 状态面就把它当全进程峰值。br 每批缓冲约 (2n+4)×1024 字节，即约 32 MiB；若多个进程都分配、都读，这部分也会重复。br 传给 halo 的四个空向量在当前入口没有解包；不能把一个并未实例填满的通信边界空间算成这条路径已发生的消耗。

一句话记住：两位可以表示一格，不等于全程序每格只占两位。

B.3　速度能推到哪一步

公式 T(P)≈T串行+T可分/P+T等待+T额外搬运 是分析模型，不是拟合结果。假设某个虚构工作流的串行部分占 10%，可平分部分占 90%，且没有等待，用 16 核的理想加速为 1/(0.1+0.9/16)=6.4。这个例子只解释为什么“16 核”不是“16 倍”；材料没有给任何版本的 10% 比例。若工作单元原本已是 64 格的一字，线程分摊的是若干个字，不是把既有的处理速率再无条件乘 64。

满分预算 68 秒与基本分预算 110 秒，按全部 64 核分别约为 8.11 和 13.11 核纳秒/逻辑格；按一个 16 核节点而不跨节点分别约为 2.03 和 3.28。项目没有提供同步的编译选项、线程绑定、输入指纹、多个重复样本与正确性记录，所以不能给九个实现排速度名次。br 第 520 行注明创建线程探针实测 1.36 秒；没有原始输入和探针运行日志，只能标“源码作者记录的局部实测”，更不能把它从未知的总耗时直接减去当新成绩。

若将来拿到记录，先比同一输入的最终森林，再把读、事件、转移、输出的计时边界逐项对齐。以同一机器同一输入的基准中位耗时 T₀ 除候选中位耗时 T₁ 才是可核对的加速比；用题目时限除自己的耗时仅代表离目标还有多远。

一句话记住：时限给预算，源码给操作数，真实秒数只能由有条件记录的实验给出。
